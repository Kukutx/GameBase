# tiamat

The reusable foundation every game in this repository shares. Each game under `games/<id>/` holds its own content, scenes and rules in its `game/`; everything here is reused by later games, games of other genres and in-game minigames, and a fix here reaches every game at once.

```text
tiamat/core/                Genre-agnostic services: content, save, session, rules, settings,
                              input, audio, world travel, depth tracks, time, randomness, triggers,
                              player vitals, player profile, playthroughs and what carries over, interactions,
                              state machines, node pools, screen shake, diagnostics, and the
                              title, pause and settings menus
tiamat/modules/items/       Items, inventory, money, storage, shops, crafting, food buffs, building placement
tiamat/modules/skills/      Skill levels, experience and perks
tiamat/modules/damage/      Health, damage and factions: what every kind of fight shares
tiamat/modules/dialogue/    Conversations: one at a time in a balloon that
                              pauses the world, from a dialogue file or a chat,
                              and spots in the world that talk when used
tiamat/modules/combat/      Fights in real time: hurtboxes, hostile         (requires damage, items)
                              creatures, enemy data, the melee attack,
                              enemy tiers by depth and the player's defeat
tiamat/modules/lifesim/     Farming, animals, fishing, forage, processing,   (requires items, skills, combat)
                              expansions, shipping, mining, calendar festivals, staying up late,
                              collections and their milestones, daily contracts
tiamat/modules/npc_social/  NPC actor, what NPCs say, schedules,            (requires dialogue, items)
                              relationships, heart events, memory
tiamat/modules/npc_ai/      NPC chats: topics, rule replies, recall of       (requires dialogue, npc_social)
                              what was said, an optional language model
tiamat/modules/progression/ Quests, mail, town projects, tool upgrades      (requires items, skills, npc_social)
tiamat/modules/roguelite/   Runs: their count, outcomes, run-long values, random streams and boons
tiamat/modules/rts/         Command battles in real time on an open field:   (requires damage)
                              units, maps, paths, the foes' play and the battle minigame
tiamat/modules/tactics/     Grid battles in active time: units, actions,     (requires damage)
                              maps, the foes' play and the battle minigame
tiamat/templates/new_game/  The project a new game starts from
tiamat/tiamat.json        Each module's required modules, addons and autoloads, the core's autoloads,
                              and the addons every game links
```

Dependency direction: a game may use `core/` and the modules its `game.json` lists; a module may use `core/` and the modules it requires in `tiamat.json`, and the requires form no cycle, so a game takes a module with only the modules below it; `core/` must not use a module, and nothing in `tiamat/` may use a game or name one of its ids (a value a game gives to `id` or to a `*_id` property in its data and scenes). `tools/check_layers.js` enforces this in validation for the foundation and for every game, with no exceptions list. A module gets game data through a slot the game fills: the mine floor table (`MineState.floor_table`, set in Farm1's `game/game_setup.gd`), a property set in the game's scene (the mine's entrance and floor spawn points, a housing's name and type, the shop stand's `shop`), a field of the game's data (what an animal eats). A game declares its input actions as `ControlAction` resources in `GameDefinition.controls`; a module declares the controls its own systems read (`GameModule.get_controls()`: the rts module's battle commands) and the core those of its own (the four moves a `TopDownPlayer` walks with, `core/input/controls/move_*.tres`, which lend their keys and buttons to the menus' `ui_*` directions as the player binds them, interact, quick save, quick load and pause), and the game lists one only to place or replace it (`GameControls`); `InputPrompts.get_move_prompt()` shows the moves on the device in use, and a gamepad's buttons are named as its maker prints them (Xbox, PlayStation or Nintendo, told from its name); an engine's menu action the game declares no control for is named from the input map (`ui_cancel`: Esc, the pad's back button, × on touch for the close button over a menu; MFarm's shop close tag). On a touchscreen the core's `TouchControls` play the game once a finger touches it: a stick at the lower left walks a `TopDownPlayer` (or any node in `TouchControlsService.MOVER_GROUP`), a button at the lower right presses each control the game marks `touch_button` (the core's interact, Ember Depths' attack), a pause button at the left edge pauses, and over a menu a close button at the top right cancels; prompts then name the buttons, and a minigame asks for the buttons it reads (`MiniGame.get_touch_actions()`, the fishing reel's interact) while the rest are tapped as the mouse. A HUD line near the bottom draws back from the stick and the buttons with a `TouchClearance` child (Farm1's hotbar and bag lines). A phone held sideways shows a game that keeps its height (`window/stretch/aspect` `keep_height`) a wider view than it was laid out in (480 x 270 becomes 600 x 270 on a 20:9 phone), so a HUD places its controls by their anchors, not their offsets alone: a corner's text keeps to its corner, a line across the screen reaches both sides and a menu stays in the middle; the core's `test_screens_fit` checks every screen of every game for this, and that what shows lies inside the view. A game whose text reads small on a phone lays its screens out in a smaller view there (`window/size/viewport_width.mobile` and `viewport_height.mobile`: MFarm's 640 x 360 becomes 480 x 270 on a phone, its text a third larger), and the fit tests hold every screen and menu to each view the game names (`ScreenFit.view_sizes()`, `MenuFit.find_overflow_in_views()`). Text reads on a phone at Android's smallest size, 12 sp on a small phone (`ReadableText`: 8 pixels in a view 270 high, 11 in Jianghu's upright view 360 wide): the core's menus raise their small print to it in a narrow view and keep their look in a wide one, and `test_screens_fit` holds every text of every screen to it in the view the game shows a phone (MFarm's date and version now 8 pixels). A phone held sideways also draws the game under its camera at one end of the screen: a HUD with a `HudSafeArea` child (every game's) moves each control that keeps to a side in from that side's unsafe strip (`TouchControls.safe_rect()`), and back when the phone is turned over; a line's `TouchClearance` then draws back from the touch controls where the line now is. A hint on a status line names its controls anew when the player picks up another device, and a phone or a browser on one starts on touch. While a thumb holds the stick, a second finger taps the world beside the controls as the mouse would (the engine makes a mouse of the first finger only). A button smaller than a fingertip (MFarm's title tabs and settings gear) takes the taps that land just beside it, up to a fingertip's square (`TouchTarget`, 7 mm measured on the screen), unless another control or another button's nearer edge lies there, so a phone's small buttons are as easy to hit as on a computer; a control of a game's own that the player taps joins `TouchTarget.GROUP` to get the same (MFarm's bag and toolbar slots). A list (a `ScrollContainer`: the settings' pages, a shop, the crafting menu) scrolls under a finger that drags it from anywhere in it, a row's button or panel too, after the finger moves a short way, so a tap there still presses the button (`TouchScroll`). When the player types on a phone (an animal's name, MFarm's trade amount, which brings up the number keys), the menu of the field rises above the keyboard as it comes up and goes back down as it goes (`KeyboardLift`). The player sets the controls' size and opacity and puts the stick on either side in the settings (`GameSettings.touch_size`, `touch_opacity`, `touch_stick_right`), which offer them on a device played by touch. Android's back button goes back the same way: it closes what is open, pauses play, or quits from the title (`application/config/quit_on_go_back` is off in every game). A control read in one minigame names its group (`ControlAction.group`, the rts battle's "Command Battle"), so it may share a key with the world's controls and the settings show it under its group's heading. A module owns only its own vocabulary, such as the tool actions it responds to (`FarmPlot.TILL_ACTION`, `MeleeAttack.TOOL_ACTION`): the items module knows a tool's action only as a name, and whoever handles one registers it (`ItemData.register_tool_action()`), a game for its own actions too. A lower module never calls a higher one; the higher one plugs in instead: a shop sells another module's goods as `ShopOffer` resources in `ShopData.offers` (lifesim's `AnimalOffer`), a module tells the state of its systems as plain data with `GameModule.get_facts()` (items the player's inventory, lifesim the events under way, progression the quests and town projects), which whoever describes the game reads through `GameModules.get_facts()` without knowing the modules (what an NPC knows, `NpcContext`), each module announces what happened in its systems on its own `<Module>Events` autoload (`NpcSocialEvents.npc_talked`, which quests count; `LifesimEvents.crop_harvested`, which a Farm1 trigger turns into farming experience), and content gates on another module's state through a `GameRules` condition (a recipe's `condition = "SKILL_LEVEL farming 2"`).

Each module wires itself into the core through registration, not through edits to `core/`: its `GameModule` class (`modules/items/items_module.gd` and the like) registers the module's kinds of content and their checks, rule keys, save sections, load steps, save blockers and new-game steps, and the core's `GameModules` autoload installs every module class the game links, so no game repeats that wiring. The game is a module of its own: `game/game_setup.gd` (`GameSetup`, a `GameModule`) installs what only the game knows (Farm1's starting animals and mine floor table, Ember Depths' save blocker in the depths). `game/game_definition.tres` (named by the `tiamat/game_definition` project setting) gives the start location, home, calendar, starting clock and items, the controls and the content packs.

Content: every piece of content is a `ContentEntry` resource of a kind its module defines (`ItemData.KIND` is `item`) and registers with `ContentDB.register_kind()`; a game lists its entries in `ContentPack` resources (`game/data/content.tres`) named by `GameDefinition.content`. Once every module has installed, `ContentDB` (`core/content/content_registry.gd`) indexes the packs and asks each entry for its problems (`find_problems()`: its fields and its references by id), each node of each location scene (`find_scene_problems()`, `get_persistent_keys()`), and each check a module registered for a whole kind (a quest chain without cycles); a problem fails validation. A release build only indexes: its content passed these checks before the export, so it takes what they proved (a location's spawn points) as given (`checked_before_export`). Code reads content through the class of its kind: `ItemData.find(&"berry")`, `QuestData.find_all()`, `WorldLocationData.find_current(get_tree())`; these read the active registry (`ContentRegistry.active`, the `ContentDB` autoload unless a test put its own content in place), so code never asks `ContentDB` for an entry itself. The running game's facts (start location, controls, calendar) come from `GameDefinition.current()`, and the check holds them to the content too: the game starts and wakes the player in locations and at spawn points of its own (`GameDefinition.find_place_problems()`), and each event it gives a sound names a signal of an autoload. What a game sets for a module is a `ModuleSettings` resource of that module's own in `GameDefinition.module_settings` (`ItemsSettings`: the starting money and items; `CombatSettings`: the vital hits take and what a defeat costs; `LifesimSettings`: the vital work spends and how late the player may stay up), which the module reads with `GameDefinition.current().get_settings()`, usually through the settings' own `current()` (`ItemsSettings.current()`); a game that lists none of a kind gets its defaults. A module registers its kind with `ContentDB.register_settings()`, so what is wrong with the settings a game runs with, listed or default (an id that names nothing), fails validation as a content problem does.

Time: the core's `WorldClock` autoload (`core/time/game_clock.gd`) counts the day and the minute of the day. How the days group into seasons and weeks, how fast a minute passes, when night falls and when the player wakes is the game's `GameCalendar` (`GameDefinition.calendar`; four 28-day seasons when it sets none), read through `GameCalendar.current()`. The time conditions (`SEASON`, `DAY_OF_SEASON`, `WEEKDAY`) and every content check of a season name follow it, so a game of two ten-day seasons validates its content against those. `WorldClock.advance_until(condition, limit)` runs the clock on, each minute as if it passed, until a condition holds: to the evening, the next market day or a festival; a wait also ends at a minute a module stops it at (`WorldClock.register_wait_stop()`: the late night lifesim sends a player who is still up home at). A location's `DayNightModulate` darkens it by the calendar's night, and a player who sleeps or passes out after midnight wakes the same day. A calendar whose minutes last no time (`real_seconds_per_game_minute = 0`, Ember Depths) stands still until something moves it, such as a rest or a defeat. `GameCalendar.get_date_text()` gives a day as the player reads it ("Spring 3", "Spring 3, Year 2", or "Day 31" for a calendar of one season); the HUD clock, the save slots and resting use it.

Randomness: the core's `GameRandom` autoload (`core/random/game_random.gd`) holds the world's seed and gives each thing that rolls dice its own stream by key (`GameRandom.stream("forage:%d:%s:%s" % [day, spawner_id, location_id])`), seeded by SHA-256 of the seed and the key. A stream (`GameRandomStream`) is the project's own xoshiro128** rather than the engine's generator, whose algorithm may change between engine versions, so the same world rolls the same weather, catches and mine floors on every load, platform and engine version, and a test pins an outcome by its seed. Besides numbers, a stream picks one of a list (`pick()`), an index by weights (`pick_weighted()`: a catch or a forage table, a weight of 0 never), a point of an area (`point_in()`) and points spaced apart in one (`scatter()`: a mine floor's rocks, an arena's enemies, clear of what a game asks). The seed is the `random` save section; a new game takes `GameDefinition.world_seed`, or a fresh seed when that is 0. Gameplay randomness never uses the global generator, which is left to cosmetic jitter such as a sound's pitch. The weather of a day is rolled from that seed with the chances the game gives each of its weathers per season (`GameDefinition.weather_odds`, in the order they are listed); a day they give no other weather has `GameDefinition.clear_weather_id`. Each weather is content (`WeatherData`, kind `weather`): its name, whether it waters what grows outside, and how the `WeatherOverlay` shows it (a tint, rain or snow, lightning). A fish, an NPC's route and `WEATHER storm` name weather by id (`WeatherState.get_weather_id(day)`), and a game that names no clear weather has none.

Stats: a number one system reads and others change (the energy a tool costs, how long a fish takes to bite, how hard an attack hits) is a stat of the core's `GameStats` autoload (`core/stats/game_stats.gd`). The module or game that reads a stat registers it when it installs (the core registers `move_speed`, which a `TopDownPlayer` walks by; lifesim `fishing_wait` and `max_energy` (`LifesimSettings.MAX_ENERGY_STAT`), which a game's energy vital may follow, combat `attack_damage`, `attack_cost`, `incoming_damage`, which a hit on the player is changed by, `max_health` and `loot_quantity`, which what a defeated enemy drops is changed by, its fraction rounded by chance with `GameRandomStream.round_by_chance()`, and `dodge_cooldown`, the wait between dodges) and reads it through `GameStats.apply()` or `get_multiplier()`. A stat the player should know of is registered with its name (`register_stat(&"attack_damage", "Attack")`, a translation key the localization check reads), so what content changes reads itself out in the game's numbers (`GameStats.describe_changes()`: "Attack +10%", "Max health +15"), in a skill perk's summary (`SkillPerk.describe()`: its name, then its changes), a boon on offer and a lasting upgrade at its stand, and `describe_current()` gives what every source makes of the stats now, which the pause menu's Bonuses page lists while there is any. What changes stats registers as a source (`GameStats.register_source()`, `unregister_source()`): the items module's food buffs and lasting upgrades, the skills module's perks and the roguelite module's boons, all content with `multipliers` and `bonuses` by stat, which `ContentDB` checks against the registered stats. A source tells when its changes changed (`GameStats.notify_changed()`), and `GameStats.changed` has whatever keeps a value read from a stat (a vital's maximum) read it again. A lasting upgrade (`StatUpgradeData`, kind `stat_upgrade`, `modules/items/upgrades/`) is bought level by level at a `StatUpgradeStand` (`stat_upgrade_stand.tscn`, a `ChoiceMenu` of its upgrades with each one's level, what it does and what its next level costs, or why it cannot be bought), for money (`money_costs`, one per level) and items (`materials`), while its `condition` holds; its level lives in the world, so it outlasts days and runs, changes stats once per level (`StatUpgrades`), and `STAT_UPGRADE_AT_LEAST`, `RAISE_STAT_UPGRADE` and `ItemsEvents.stat_upgraded` follow it. Ember Depths' camp forge sells five. Skills are content too (`SkillData`): the game defines its skills, their levels and their perks, and grants experience for the module events it chooses with triggers.

Conditions and actions: content says when something is available and what it does with short text keys (`condition = "HAS_ITEM berry 3, !QUEST_COMPLETED first_harvest"`), parsed by `core/rules/game_query.gd` and evaluated by the `GameRules` autoload. The core registers time, weather, location, flag and vital keys; each module registers its own (`modules/items/items_rules.gd`, `modules/skills/skills_rules.gd`, `modules/lifesim/lifesim_rules.gd`, `modules/npc_social/npc_social_rules.gd`, `modules/progression/progression_rules.gd`) when it installs, with argument kinds of its own (`SkillsRules.ARG_SKILL`), a check of arguments that depend on each other (a level the named skill reaches) and the requirement in words a menu shows for what is locked (`GameRules.describe()`: "Mining Lv3", "Complete Garden Fund", "From day 5", each entry by the name the player reads, `GameRulesService.entry_name()`): a station's minigame, a tool upgrade, a recipe in the crafting menu and an expansion say what they still need. The conditions a player works toward have one (a day, a season, the weather, a place, an achievement, a quest, a project, items, money, hearts, an event, a milestone, runs, a won minigame); flags, options and event arguments, which the player does not read, have none. Every key content uses is checked at startup, so a typo fails validation. Whatever gates content on the state of the world is such a condition, in a `condition` field: a letter (`QUEST_COMPLETED first_harvest`), a heart event or an expansion (`PROJECT_COMPLETED garden_fund`), an NPC's route (`EVENT_ACTIVE spring_fair`). A system answers questions about its own state through its keys and never copies that state into world flags for others to read, so there is one source of truth and a misspelt id fails validation. A field stays only where the owning system plans with it, such as a crop's seasons, an event's date or a heart event's hearts (the order events play in). `WorldState` is the flag store for facts no system owns (`WORLD_FLAG`, set by dialogue or actions): booleans through `get_bool`, counters through `get_int`/`add_int`.

Events: content listens to what happens through events (`core/rules/game_event.gd`), each a signal of an autoload written `<Autoload>.<signal>` (`LifesimEvents.crop_harvested`), whose arguments it reads by name; `GameEventListener` connects code to one the same way. An argument named `<kind>_id` (or ends in `_<kind>_id`) holds an id of that kind of content (`crop_id`, `mining_node_id`, `result_item_id`), so the ids content compares it with and the keys it passes it to are checked at startup; an argument `position` (a `Vector2`, global) says where in the world it happened, as the world events of the items, lifesim and combat modules do, so its sound plays from there. [docs/reference/events.md](../docs/reference/events.md) lists every event of the foundation.

Triggers: what content does when something happens is a trigger (`core/rules/trigger_data.gd`, kind `trigger`): an `event`, a `condition` and `actions`, which the core's `GameTriggers` autoload runs when the event fires and the condition holds. The condition and actions see the event's arguments by name: `EVENT_ARG crop_id turnip` and `EVENT_ARG_AT_LEAST quantity 3` test them, an argument written `$name` passes one on (`ADD_SKILL_XP combat $combat_xp`), `repeat_per = quantity` runs the actions once per unit, and `once` fires a trigger once per world (an action that fails after others ran leaves it pending, and the next time the event fires it resumes there with the arguments of the event that set it off, each in its type, unless a content update changed its actions; a once trigger does not repeat, and its event declares only booleans, numbers, text and positions, which a save keeps). A trigger's event and the arguments it reads are checked at startup, and the values an event passes are checked as written arguments are when it fires: a value that fails makes the condition false, whatever surrounds it, and runs none of the actions. What a save's restore or a new game's setup announces, until the player stands in the location, fires no trigger. Farm1 grants its skill experience this way (`game/data/triggers/`), so a game wires its modules together in data rather than in code.

Quests: a quest (`modules/progression/quests/quest_data.gd`) asks for one or more `objectives` (`QuestObjective`), each counted from an event of any module the way a trigger listens to one: its `event`, a `condition` on the event's arguments (`EVENT_ARG crop_id turnip`, or `ITEM_TAG $item_id fish` for every item tagged fish), `count_per` an integer argument (`quantity`) and the `required_amount`; with a `measure`, an autoload's method returning an int (`MineState.get_deepest_floor`), it follows that number instead of counting. `QuestState` listens only to the events of the active quests' objectives, pays the reward once every objective is met and saves each objective's progress, so no quest code names the modules whose events its quests count.

Player profile: the core's `GameProfile` autoload (`core/profile/game_profile.gd`) keeps what outlives every save of a game in `user://profile.json`: the achievements the player unlocked (`AchievementData`, a kind of content) and profile flags, booleans and counters as `WorldState` keeps a world's. A new game, a load or a deleted slot leave it alone. Reading the file keeps only what is well formed and names current content; a change that could not be written is written with the next one or at quit, and the player is told once. Content reaches it through rule keys (`UNLOCK_ACHIEVEMENT`, `ACHIEVEMENT_UNLOCKED`, `SET_PROFILE_FLAG`, `ADD_PROFILE_FLAG`, `RAISE_PROFILE_FLAG` for a best that only rises, `PROFILE_FLAG`, `PROFILE_FLAG_AT_LEAST`), usually from triggers: An achievement that counts a profile counter toward a goal (`progress_flag`, `goal`) needs no trigger: the profile unlocks it as the counter reaches the goal (`GameProfile.get_progress()`). Farm1 unlocks Green Thumb with a trigger on its first harvest, and counts every save's crops toward Seasoned Farmer (`ADD_PROFILE_FLAG crops_harvested $quantity`, `goal = 100`). A storefront's achievements follow `GameProfile.achievement_unlocked`. A game's HUD shows the unlock, as every toast, on a `StatusLine` (`core/events/status_line.gd`), which shows messages sent together one after another rather than only the last. The title and the pause menu's Achievements, shown while the game has any, list them (`AchievementsMenu`, `core/ui/achievements_menu.gd`): how many are unlocked, those unlocked first in the order they were, then those still locked in their `order` (Iron Banners' read as the way through its campaign), dimmed, each with its icon, one that counts toward a goal showing how far the player is, a `hidden` one keeping its name and description to itself until it is unlocked. Under them, Records lists the numbers the profile keeps across every save, each a `RecordData` (kind `record`, `core/profile/record_data.gd`) that names its profile counter and its place (`flag`, `order`, as every kind with an order is sorted, `ContentEntry.listed_before()`): Farm1's crops harvested, deepest mine floor (`RAISE_PROFILE_FLAG deepest_mine_floor $floor`) and mine guardians felled, Ember Depths' deepest depth.

Hints: a tip the player reads once is content, a `HintData` (kind `hint`, `core/profile/hint_data.gd`) with its text, which names a control by its action in braces (`{interact}`, `{move}`) so it reads as the key or button the player uses for it now. A trigger shows one with the action `SHOW_HINT <hint>` on the event that makes it useful (`GameSession.new_game_started`, the first `CombatEvents.player_hurt`), and `HINT_SHOWN <hint>` asks about one. The profile keeps which hints showed, so each shows once across every save, and none shows while the player turns hints off in the settings (`GameSettings.hints`); one passed over then shows the next time once they are back on. A HUD's `StatusLine` with `shows_hints` shows them, each for longer than a toast (`seconds_per_hint`), and the pause menu's Tips, beside its Settings once a hint has shown, lists every hint the player has seen to read again (`TipsMenu`), each naming its controls as the device in use performs them. A list menu's entries are `MenuEntry` rows (`core/ui/menu_entry.gd`) the keys and a gamepad walk through, the list scrolling with them.

Conversations: the dialogue module (`modules/dialogue/`) shows one conversation at a time through its `Dialogue` autoload, in a `DialogueBalloon` along the bottom of the view that holds the controls and pauses the world while it shows: the lines of a dialogue file of the Dialogue Manager addon from one of its titles (`Dialogue.show_dialogue()`) or those of a chat made while it runs (`Dialogue.show_chat()`, a `DialogueChat`). `Dialogue.finished` says a dialogue file was read to its end; a balloon that goes first (a load, the title) only gives the controls back. A game puts a `DialogueSpot` (`dialogue_spot.tscn`) where something talks when the player uses it, a sign or a camp's keeper, naming its dialogue file and title; content checks that the title is there. The npc_social module's NPCs talk through it, so a dungeon or a strategy game talks without NPCs: Ember Depths' Old Delver and Iron Banners' captain are such spots.

Playthroughs and what carries over: the core's `Playthrough` autoload (`core/playthrough/playthrough_service.gd`) numbers the playthrough a save belongs to, and `PLAYTHROUGH_AT_LEAST` lets content ask for it. A game lists what a new playthrough carries over in `GameDefinition.inheritance`, each an `InheritanceRule` with a key: `WorldValueInheritance` (world values under some prefixes), the items module's `MoneyInheritance` (a share of the money) and `ItemInheritance` (items with some tags) and the skills module's `SkillInheritance` (a share of each skill's experience). `Playthrough.start_next()` takes each rule's part of the game as it is and starts a new game that begins with it. A sequel carries a game over the same way: `write_legacy()` writes the parts by key to `user://legacy.json`, and the sequel reads it (`PlaythroughService.find_legacy("<the game's name>")`) and starts from it (`start_from_legacy()`), each of its rules taking the part with its key.

Depths and runs: a place that goes down depth by depth keeps its depth and the deepest one reached in a `DepthTrack` (`core/world/depth_track.gd`), in the world under its key, with an optional bottom, checkpoints to return to and a random stream per depth: Farm1's mine (`MineState`) and Ember Depths' depths both use one. The roguelite module's `RunState` (`modules/roguelite/runs/run_service.gd`) counts the runs a world started, keeps values that last one run and a random stream per run, and ends a run with an outcome: back at camp (the game says so), defeated, or abandoned when the player passes out for another cause (lifesim's late night), a load, a new game or the title takes them out of play (passing out autosaves what the run brought). While a run goes on the game cannot be saved, unless the game lets it (`RunState.blocks_saves`); `RunState.run_started` and `run_ended` are events triggers follow, and `RUN_ACTIVE` and `RUNS_AT_LEAST` are its rule keys. A run takes boons (`BoonData`, kind `boon`): changes to stats that last the run (`multipliers`, `bonuses`, once more each time taken, up to `max_stacks`; `RunState` is a `GameStats` source) and actions run when taken. The player picks one of a few the run offers (`RunState.offer_boons(count, name)`, as likely as each one's `weight`, among those whose `condition` holds, rolled from the run's stream so the same place offers the same) at a `BoonAltar` (`modules/roguelite/runs/boon_altar.tscn`, one boon a run each), or content gives one (`TAKE_BOON`); `BOON_TAKEN` and `BOONS_AT_LEAST` ask about them and `RunState.boon_taken` tells of each; a `BoonLine` in the HUD tells the run's (`RunState.describe_boons()`). Each boon belongs to a pool (`BoonData.pool`, empty the common one) and an altar offers one pool's (`BoonAltar.pool`), so a game keeps apart its altars' boons or its pacts, a burden with a reward a run starts under (Ember Depths' way down offers them after the first run). A boon's condition can follow the player's profile (`ACHIEVEMENT_UNLOCKED`), so later runs find more. Ember Depths lights an altar on each cleared floor. A run counts tallies (`RunTallyData`, kind `run_tally`: the creatures it defeated, the depth it reached), which content adds to with `ADD_RUN_TALLY <tally> [amount]` (a trigger on `CombatEvents.enemy_defeated`) and code with `RunState.add_tally()` or `raise_tally()`; `RUN_TALLY_AT_LEAST` asks about one and `RunState.tally_changed` tells of each change. A tally with a `best_flag` keeps the best of any run in the profile, which a `RecordData` or an achievement's progress shows. A run that ends, not abandoned, leaves a report (`RunState.get_last_report()`: "Run 3 · Returned" and a line for each tally and the boons, a tally that beat an earlier run's best marked "New best"; a game names its own outcomes in `RunState.outcome_names`), and a `RunSummary` node in the scene the player comes back to tells it once nothing holds the controls (`ChoiceMenu.tell()`). The world remembers the last ten of those reports (`RunState.get_history()`, what each tally and boon stood at as well as its lines, read in the player's language now), and the pause menu's Runs page lists them, newest first.

Places and travel: every place the player can be is a `WorldLocationData` (kind `location`) with its scene, spawn points and an optional region (`RegionData`, kind `region`). `WorldTravel.travel_to(location_id, spawn_id, params)` changes the scene behind the core's fade (`Transition`), and `await WorldTravel.go_to(...)` also waits until the player stands there. The `params` a travel carries (the floor to open, the door used) are the place's to read with `WorldTravel.get_params()` from its `_ready()` on. Arriving in a location of another region fires `WorldTravel.region_changed` (a load enters the region of its scene too), and `REGION valley` asks where the player is; a load and the title forget the last travel's parameters. A cutscene covers the screen without changing the scene with `await Transition.cover(self)` and clears it with `await Transition.uncover()`; a travel under the cover leaves the screen covered, the cover ends with the cutscene node if it is freed first, and a load or the title gives it back. `await Transition.wait_until_clear()` waits until no change, cover or fade shows. A wait that has to wait resumes on a later frame rather than inside a signal, so what waited may free nodes or travel on at once.

The view: a game puts the core's `GameCamera` (`core/camera/`) on its player. It follows the player smoothly, but where the player is put rather than walked (a travel's spawn point, a load: `WorldTravel.place_player()`) it shows them at once instead of sweeping across the map. A location sizes a `CameraBounds` over its map to keep the view inside it; `zoom_to()` eases the zoom, and `GameCamera.shake_view(node)` shakes the view for a moment (nothing shakes with reduced motion).

Vitals and money: what the player counts down and refills (health, energy, mana) is content, each a `VitalData` (kind `vital`) with its name, its maximum and whether a night's sleep refills it, and the core's `Vitals` autoload (`core/player/player_vitals.gd`) holds the player's. A vital's maximum may follow a stat (`VitalData.maximum_stat`, combat's `max_health`, lifesim's `max_energy`): a boon, a food buff, a skill perk or a lasting upgrade that raises the stat raises the maximum, which comes filled, and one that ends takes the value down with it. Work and attacks spend a vital (`try_spend()` tells the player when there is not enough), food and rest restore it (an item's `restores`, by vital id, used with `InventoryState.consume()`), and `depleted` fires when one reaches 0. The core gives no vital a meaning: the module that uses one names it in its settings, so a game that leaves `LifesimSettings.energy_vital_id` empty has free tools, and one without `CombatSettings.health_vital_id` has hits that hurt nothing. `VITAL_AT_LEAST` and `RESTORE_VITAL` are their rule keys and `Vitals.describe_all()` gives them as a HUD shows them. Money is the items module's `Wallet` (`modules/items/wallet/`), with `MONEY_AT_LEAST` and `ADD_MONEY`. A module that knocks the player out calls `await GameSession.pass_out(cause, recover)`: `GameSession.passing_out` fires, the player's activities end, `recover` restores or takes what the cause does (before the night's payouts arrive), the clock moves to the next morning, and the player wakes at home and the game autosaves (`passed_out`). Combat's defeat is one cause, lifesim's late night (`LateNight`) another: a player still up at `LifesimSettings.late_night_minute` wakes with `late_night_energy_percent` of their energy and `LifesimEvents.stayed_up_late` follows.

Combat: what every kind of fight shares is the damage module (`modules/damage/`), which needs no items, so the rts and tactics modules take it alone: `Health` (between 0 and a maximum, `depleted` at 0), `Damage` (an amount, the faction it comes from, its source and its knockback) and `FactionData` (any two factions fight unless one lists the other among its `allies`; an id alone names a side, such as `player` and `monsters`). The combat module fights in real time: an actor is hit through its `Hurtbox` (`modules/combat/combat/hurtbox.gd`), which takes damage of a hostile faction only, flashes the actor, pushes it back and then takes no hit for `invincible_seconds`; the player's `PlayerHurtbox` drains the game's health vital (`CombatSettings.health_vital_id`), staggers the player while the push carries them (`TopDownPlayer.stagger()`) and shakes the screen with the core's `GameCamera` (`GameCamera.shake_view()`, which does nothing with reduced motion). `MeleeAttack`, a child of the player, swings the weapon selected in the hotbar (an item whose tool action is `attack`) at every hostile hurtbox it overlaps, for the weapon's power changed by `attack_damage`, spends its `cost` (changed by `attack_cost`) of the attack vital (`CombatSettings.attack_vital_id`; none, and swings are free), draws its arc (`SwingEffect`, kept in a `NodePool`) and swings again after `cooldown_seconds`. A `RangedAttack` beside it shoots a bow on the same control (an item whose tool action is `ranged_attack`): a `Projectile` the way the player faces, or at the nearest foe within `aim_assist_degrees` of that way and in reach with no wall between, for the same stats and vital (`WeaponUse`, what both attacks share). A `DodgeRoll` beside them rolls the player out of the way on the game's `dodge` control: a short dash the way the player moves or faces (the core's `TopDownPlayer.dash()`) during which no hit hurts them (`Hurtbox.make_invincible()`), then a moment before the next (the `dodge_cooldown` stat, `DodgeRoll.COOLDOWN_STAT`, which Ember Depths' Ember Step boon halves), for a `cost` of the attack vital if the game sets one (Ember Depths: Shift, the pad's B button, a touch button). A `HostileCreature` runs on a `StateMachine` (idle, chase, windup, hurt, defeated) and strikes the player's hurtbox, at once or, given `EnemyData.windup_seconds`, after standing and glowing that long, so the player can step out of reach or stun it first (every guardian winds up), or with `EnemyData.shot_speed` shoots at them from its `attack_range` (a `Projectile`: a glowing ball that passes its own side, a wall stops and a step aside dodges) and backs away from a player who comes near (Ember Depths' Ember Wisp); chasing the player or stunned by their hit, it hunts them, and `FightState` (`modules/combat/fight/`) makes a fight of that: it starts with the first hunter (`CombatEvents.fight_started`), plays the game's fight music over the location's while it lasts (`CombatSettings.fight_music_cue_id`) and ends `fight_calm_seconds` after the last hunter gave up or fell, at once when the player leaves the scene (`fight_ended`). `CombatEvents.attack_swung`, `enemy_hurt`, `player_hurt` and `enemy_defeated` are events a game maps to sounds, the creature's from where it stands. Any creature can come in an elite form (`EliteData`, a kind of content: Ember Depths' Hulking, Swift and Searing), set as `HostileCreature.elite` before it enters the tree: its health, hit, speed and size scaled, its colour tinted, its name changed ("Hulking Slime"), more experience and more of its drop, and `CombatEvents.elite_defeated` after `enemy_defeated`; a place that spawns creatures rolls one with `EliteData.roll()` from a stream of its own, among the elites whose `condition` holds, and a place generated by depth with its `EliteOdds` (a chance from a depth on, rising with each depth below up to a most): Ember Depths' floors, and the lifesim mine's (`MineFloorTable.elite_odds`, Farm1's Giant and Frenzied slimes from floor 10). A place generated by depth lists its enemies as `EnemyTier` entries, each from its minimum depth on and up to its `maximum_depth` when it has one: Farm1's mine floors and Ember Depths' floors. A guardian tier (`guardian_every`) spawns its enemy only at the depths it guards, every so many from its minimum depth (`EnemyTier.guardians()`), and never among the ordinary ones (`reached()`, `deepest()`): Ember Depths' Ember Warden every fifth depth, and in Farm1's mine (`MineFloorTable.get_guardian_ids()`) a Slime King on floors 25 and 50, then a Void Monarch every 25th floor from the 75th. A mixed tier (`share`) never leads a depth of a place that spawns one kind a depth, but that share of its enemies come as its own among the kind that leads (`EnemyTier.pick_mixed()`, rolled from a stream of the depth's own): Farm1's Spitting Slimes among the Blue Slimes of floors 21 to 39. The lifesim mine lays a guarded floor out with its guardians furthest from the way in and half the ordinary enemies, names them on arrival, opens the ladder once they fall, and its elevator names the guardians still standing on a stop (`MineRunState.get_standing_guardian_names()`, by `HostileCreature.is_down()`, which reads a saved creature before its scene loads). An `EnemyData`'s `sprite_tint` recolours its art, so one sheet serves several enemies. A `Hazard` (`modules/combat/combat/hazard.gd`) is a danger of the ground that flares on a cycle: it rests, glows `warn_seconds` to warn, then for `active_seconds` hurts each hurtbox it touches once a flare and pushes it away from its middle, of every side when it has no `faction`, so a creature lured onto it burns too; `phase_seconds` has hazards side by side flare in turn, and with no rest it never stops. A place generated by depth spreads them with a `HazardSpread`: none above `from_depth`, one more every `every` depths up to `most`, `spacing` apart and clear of what stands on the floor (`spread()`), each made from its `scene` (none: a plain hazard), burning harder the deeper and started a rolled share into its cycle (`make()`), and added under the place's actors (`Hazard.add_under_actors()`): Ember Depths' ember vents from depth 3, and the lifesim mine's (`MineFloorTable.hazards`, in each floor's layout), Farm1's magma vents from floor 40. When the health vital runs out (or a load or another cause of passing out leaves it empty), the combat module's `PlayerDefeat` (`modules/combat/defeat/`) passes the player out with the cause `defeat`: they wake at home with every vital full and `CombatSettings.defeat_money_loss_percent` of their money gone, and `CombatEvents.player_defeated` says what it cost.

NPC chats: an NPC whose profile allows it (`NpcProfileData.ai_enabled`) chats instead of reading its lines, in a game that lists the npc_ai module: the module makes `ConversationService.chat_maker` a `NpcAiChat` (`modules/npc_ai/chat/`), which the dialogue module shows as it shows a dialogue (`Dialogue.show_chat()`), so a due heart event still plays first. The NPC greets the player for the moment (a first meeting, a second talk the same day, a birthday, a long absence since their last talk of any kind, the time of day), then offers the topics the game wrote for it (`ChatTopicData`, kind `chat_topic`, with a `condition`) and a goodbye; every line said goes into the NPC's memory (`NpcMemory`). The `NpcAi` autoload (`modules/npc_ai/ai/npc_ai_service.gd`) answers one request at a time: by the game's rule replies (`NpcRuleProvider`, which picks a reply whose placeholders such as `{weather}` or `{activity}` all have values, picked by the NPC, the day and the talk so far), or by a language model the game names in its `NpcAiSettings` (`GameDefinition.module_settings`: an HTTPS endpoint in the OpenAI or Anthropic chat format, or an HTTP one on the same machine for development, its model, how long a line may take, how many messages it sees), only once the player allows online services in the settings. The model gets the NPC's persona and what it knows (`NpcContext`), the latest messages and the older ones that bear on what the player says (`NpcMemoryRecall`, by shared words, Chinese by pairs of characters), and its answer is cleaned to one short line (`NpcAiText`) and shown as plain text. When the model fails, answers nothing or is slow, the rules answer, so a chat never needs the network. A key for the endpoint comes from an environment variable, read only by a debug build (`api_key_environment`), never from a game's files, and a request follows no redirect; a released game points at an endpoint of its own that holds the key.

Menus: the core ships the title screen, the pause menu and the settings menu (`core/ui/`). A game makes `res://tiamat/core/ui/title_screen.tscn` its main scene, and the title takes the game's name and description from `project.godot`. A game whose old title looked its own way keeps that look with a title of its own that extends `GameTitleBase` (`core/ui/title_base.gd`): the base opens a slot (continuing its game, or starting one there), deletes a slot after asking, opens the settings and quits, and the game's title only shows the slots (MFarm's paper menu is one). Every menu, the core's and the modules', draws with the project theme a game sets in `project.godot` (`gui/theme/custom`); a new game starts on the core's `core/ui/default_theme.tres`, whose panels are opaque, so a menu's text never runs into the screen behind it. Text shows in the font the core ships, Noto Sans SC (`core/ui/fonts/`), which `GameSettings` makes the font of the engine's default theme as the game starts (`GameFont.use()`), so every text shows in it unless a game's theme names another: it holds Latin, Chinese punctuation, the characters of GB 2312 and every character the repository's text uses, cut down by `node tools/subset_font.js`, since a web build has no system fonts to fall back on; the core's `test_theme_font` checks every translation a game registers against the font it shows in. A game puts the pause menu (`core/ui/pause_menu.tscn`) in its HUD; the core's `pause` control (Esc, Start) opens it, and it saves, loads (quick load too, after asking), opens the settings, returns to the main scene and quits, offers the pages modules add (`PauseMenu.add_page()`, each a button that shows lines over the menu while it has any: the items module's Items, what the player carries with what each is and where to get more, the skills module's Skills, each skill's level and experience toward the next and its perk, the core's Challenges, the minigames the player picks by name at a station (a campaign's battles) with their wins in this save, best scores and stars, or what a locked one needs, the combat module's Bestiary, every kind of creature the player has defeated across every save (`Bestiary`, the profile's `defeated:<enemy id>` counters) weakest first with how often it fell, its health at the player's foe strength, how hard it hits and what it drops, with each elite form of it defeated under it (`defeated:<elite id>:<enemy id>`); the profile also counts the kinds met (`kinds_defeated`), which an achievement for meeting every kind counts toward its goal (Ember Depths' Know Thy Foe, Farm1's Monster Scholar), and the core's Bonuses, what changes the player's stats now, every boon, perk, buff and upgrade added up; a game whose own menu shows one leaves it out with `hidden_pages`, as Farm1 does its items and skills), and opens when the window loses focus (the player turns to another app or browser tab) or the gamepad in use disconnects, over a minigame too, which stands still under it; the touch controls let go then too. A game whose old pause menu looked its own way lays it out itself: its scene names the controls `%Resume`, `%Save`, `%Load`, `%Settings`, `%ReturnTitle`, `%Quit` and `%Status` wherever it puts them (`%Tips` and `%Achievements` where it offers those, and a container `%Pages` for the pages), or a script extending `PauseMenu` builds them before `super()`, and the core does the rest and adds the settings menu and its questions (MFarm's paper menu is one). The settings (`GameSettings`) cover volume (the core adds the Music and Sounds buses a game's bus layout lacks), display (a phone draws at most 60 frames a second and the battery saver 30: `get_frame_rate_limit()`; the screen stays on only while the time played runs, so it sleeps on the title and under the pause menu: `GameSession.is_keeping_screen_on()`; a computer's window opens where the player left it, at the size they gave it and maximized if it was, `WindowMemory`, while a phone stays full screen with its system bars hidden), autosave, how fast dialogue types out (`get_seconds_per_character()`), language, accessibility, online services (shown only while a module uses one, `register_online_service()`, and off until the player turns them on) the rebinding of each control's key or mouse button and gamepad button (`GameSettings.bindings`, a `ControlBindings`), and the choices a game and its modules leave to the player beyond those: each a `GameOption` (a switch, one of a few named choices or a number in a range) the game lists in `GameDefinition.options` or a module declares (`GameModule.get_options()`), which the settings menu shows on its main page (`GameOptionRows`) and `GameSettings` keeps with the rest (`get_option()`, `set_option()`, `option_changed`; the dialogue module's auto-advance moves a line on by itself once the player has had time to read it, the combat module's damage taken lets the player have hits land light or heavy, `PlayerHurtbox.DAMAGE_TAKEN_OPTION`, and its foe strength gives the creatures less or more health, `HostileCreature.STRENGTH_OPTION`, the rts and tactics modules' battle speeds run a command or grid battle slow or fast, `RtsBattleGame.SPEED_OPTION`, `GridBattleGame.SPEED_OPTION`, and their foe strengths start the player's foes with less or more health, `RtsBattleGame.FOE_STRENGTH_OPTION`, `GridBattleGame.FOE_STRENGTH_OPTION`); a game lists a module's option to replace it, and content reads them as conditions (`OPTION difficulty Hard`, `OPTION_AT_LEAST <option> <n>`), so a trigger, a recipe or a quest can follow a game's difficulty. A game without weather does not show the weather effects toggle. The items module's shop menu sells, one at a time, every item the inventory holds that has a price. Where the player gets each item is found from the content (`ItemSources`, `modules/items/items/item_sources.gd`): each module that gives items registers a finder when it installs, the items module for a shop's stock, a recipe's craft or dish, the start items and every `ADD_ITEM` action of content (`GameQuery.find_action_args()`), combat for an enemy's drop, lifesim for a harvest, a fish, a forage, a vein, an animal's product, a machine's output and a festival's or milestone's reward, progression for a quest's, a project's and a letter's rewards and a tool's upgrade, each a phrase the player reads ("Sold at Village General Store", "Dropped by Slime King"); a game registers its own (a chest of its world, a gift in a dialogue) from its `GameSetup`. The items module's `test_item_sources` fails in a game with an item the player has no way to get.

Sound and music: `GameAudio` (`core/audio/`) plays every sound and piece of music by a cue id (`AudioCueData`), never a file. One piece of music plays at a time, each fading in over its cue's `fade_seconds` while the one before fades out: the location's (`WorldLocationData.music_cue_id`), or music pushed over it (`push_music(layer, cue)`: a fight's, a minigame's) until it is popped, when the music beneath comes back where it stopped. Sounds play up to `SFX_CHANNEL_COUNT` at once (and as many from places in the world) and each cue at most `max_voices` times at once, the oldest giving way; a sound played at a place (`play_cue_at()`) is heard from there, fainter up to its cue's `hearing_distance`. The game maps events to sounds (`GameDefinition.event_cues`), and sets the sounds of the menus (`menu_focus_cue_id`, `menu_press_cue_id`, `menu_open_cue_id`, `menu_close_cue_id`): a menu opening and closing (`GameEvents.menu_opened`, `menu_closed`, which every `MenuLayer` and the settings tell), any button pressed and the focus moving with the keys or a gamepad, the most telling of them once a frame. A sound is felt as well when its cue rumbles (`AudioCueData.rumble`, `rumble_seconds`): the gamepad in use shakes, its heavy motor joining for a hard blow, or the phone the player plays by touch does (`Haptics`, which a game calls with `pulse()` for anything else); a sound at a place shakes less the farther it is, nothing shakes on a keyboard, and the player turns it off in the settings (`GameSettings.vibration`), which offer it with a gamepad or on a phone. Every game's Android preset asks for the vibrate permission, which `tiamat.json` `android_permissions` names for the core. The content check names a cue that is missing or of the wrong kind, or that rumbles wrong. A cue without a stream is a slot waiting for its audio and plays nothing, though it rumbles: the games ship no audio yet ([docs/AUDIO.md](../docs/AUDIO.md)), and Ember Depths and Farm1 shake on a blow all the same.

Saves: the core's `SaveManager` keeps as many slots as the game sets (`GameDefinition.save_slots`, three by default), each with the player's own save and an autosave apart from it, so an autosave never replaces what the player saved, and each of those with a backup and an interrupted save it can recover from. A slot continues from the newer of its two saves, the pause menu loads the player's own, and a load deletes the other one when it is newer, so Continue never brings back what the player went back from. Where the game was is a section of the save like any other (`place`: the location, and the player's position when a player walks the world), so a game with no one walking its world, cards or a visual novel, saves as well. The title screen shows what a slot holds: the date and time, where the player stands, the time played (`GameSession.get_play_seconds()`, the save's `session` section) and what the modules and the game add with `SaveManager.register_slot_detail()` (the items module's money, Ember Depths' deepest depth). `AutoSave` saves the slot's autosave every few minutes, after each travel, when the player passes out, when the window closes, when a phone sends the game to the background and when the window loses focus (all a browser tells a web game before its tab is closed or left behind), and in a browser that keeps no files for the page (private browsing; `GameSaveManager.saves_persist`) the title says that progress ends with the page; a game puts a `SaveIndicator` (`core/ui/save_indicator.gd`) in its HUD to show that it did, and an autosave that fails is a toast with the reason. Every message of a save or a load is a sentence for the player, and the log names the file that could not be written.

Controls and pause: the core's `InputLock` autoload (`core/input/input_lock.gd`) holds the player's controls and the world's pause by reason. The core's and the modules' menus extend the core's `MenuLayer` (`core/ui/menu_layer.gd`), which takes `InputLock.lock(&"shop_menu", true, self)` while it shows, closes on `ui_cancel` and is found by its id as a group. Whatever offers the player a choice asks with `var id := await ChoiceMenu.ask(self, choices, title)` (`core/ui/choice_menu.gd`): a list of `ChoiceMenu.Choice`s, each a button with the lines under it, locked ones disabled, which gives the id picked or `&""`, with lines above the list when `body` says what it is about; a minigame station lists its minigames in it, the mine's elevator its floors and Ember Depths' way down its shortcuts. Whatever only tells the player something shows it with `ChoiceMenu.tell(self, title, lines)`, the lines and one choice, OK (a run's report). A conversation (the dialogue module's `DialogueBalloon`, along the bottom of the view whatever its size) pauses the world too, so the clock stands still while the player reads, a fishing cast takes a lock that does not pause, and the player acts only while nothing holds a lock. Locks add up, so a menu that closes while a minigame runs leaves the world paused, and a lock with an owner node is given back when the owner leaves the tree. They also stack as modes: the latest lock is on top, and a menu or minigame reads its keys only while its own lock is (`InputLock.is_top(self)`), so a menu opened over a minigame takes the keys and `ui_cancel` closes only the topmost menu. Nothing else sets `SceneTree.paused`, which `tools/check_code.js` checks with the other code guardrails: a script has at most 500 lines (a test at most 1000), nothing the game ships loads a resource from `user://` or saves one at runtime, and player data is read as JSON, never with `ConfigFile` or `str_to_var()`, whose text can name a resource to load or an object to build.

Building blocks: a `StateMachine` (`core/flow/state_machine.gd`) runs named states, each with what it does on entering, on every update and on leaving, for a creature's idle, chase and attack or a door's shut, opening and open; a state changes it with `change()`, and a change asked for during another follows it. `NodeRegistry` (`core/nodes/node_registry.gd`) finds a node by an id it registered under (a boss a cutscene speaks to, a door a switch opens) until it leaves the tree. `NodePool` (`core/nodes/node_pool.gd`) keeps instances of a scene (hit sparks, damage numbers) to use again rather than make and free them each time; an instance that must start over resets itself in a `reuse()` method.

Grid battles: the tactics module plays a battle on a grid in active time. A game writes its maps (`BattleMapData`, kind `battle_map`: the grid's size, its blocked cells, the cells that give cover, where a unit takes `cover_reduction` less damage, 30% unless the map says otherwise, the rough ground, which takes `rough_cost` steps to enter, so a walk goes around it when that is shorter (`BattleGrid.walk()` and `path()` count the steps), the side the player commands and where each unit starts, a unit with a `condition` joining only while it holds, such as a reinforcement once another battle is won), the units (`BattleUnitData`, kind `battle_unit`: health, attack, defense, speed, move and actions) and their actions (`BattleActionData`, kind `battle_action`: damage or a heal, its power, its range in steps and the area it reaches). `AtbBattle` (`modules/tactics/battle/atb_battle.gd`) is the battle as plain data on a `BattleGrid`: every unit's gauge fills at its speed, a full gauge gives a turn of one move and one action in either order (one that skips either comes back sooner; until the unit acts, the player may take its move back, `undo_move()`, unless a foe took a turn since), the player commands the units of their faction and `GridBattleAi` plays every other, allies of the player included, striking for the same good from where the fewest of its foes could strike back (`AtbBattle.get_threats()`), and from cover before the open (`BattleGrid.is_cover()`, damage through `AtbBattle.amount_of()`, which the forecast tells too), and the battle ends when no two living units are hostile (`FactionData`), won when the player's side is left. Whether time goes on while the player picks a command and how fast it runs are the game's `TacticsSettings`. Health is the damage module's `Health`. The same battle with the same commands plays the same way, so a test fights one with no view. The module's minigame (`modules/tactics/view/grid_battle_game.tscn`, setting `map`) shows a battle on a board scaled to the view, with the unit whose turn it is and its commands (scrolling in a short view), the units whose turns come next numbered on the board (`AtbBattle.get_turn_order()`), the cells a command may pick and what an action reaches, while a move is picked the cells the foes could strike on their next turns (`AtbBattle.get_danger()`), while an action is aimed what it would do to each unit it reaches (`AtbBattle.forecast()`), played with the move keys and interact or the mouse, or on a touchscreen by tapping a cell to see it and again to pick it, a move taken back with Undo Move in the place of Move; it tells `TacticsEvents.battle_ended` and `foe_defeated`, and wins with the units of the player's side left as its score. A minigame definition that sets a map the content lacks is a content problem.

Command battles: the rts module plays a battle in real time on an open field. A game writes its maps (`RtsMapData`, kind `rts_map`: the field's size in pixels, the rectangles no unit walks through, the side the player commands, where each unit starts (a unit with a `condition` joins only while it holds) and whether the other side marches on its foes or waits for them) and the units (`RtsUnitData`, kind `rts_unit`: health, damage, armor, attack range and cooldown, speed, sight and size, and `heal` for a healer, which mends instead of fighting). `RtsBattle` (`modules/rts/battle/rts_battle.gd`) is the battle as plain data in fixed steps: units walk the ways `RtsNavigation` finds (a straight line when it is clear, else a path through open cells with its corners cut) and keep out of each other's way, a group sent somewhere spreads over places of its own, and a unit attacks a foe in reach once its cooldown is over, for its damage less the foe's armor, while a healer goes after the most hurt friend it sees and mends it (`RtsTargets` chooses what each goes after; healers alone hold nothing, so a side of only healers has lost). The player orders their faction's units to move, attack a foe, attack-move (fighting what they see on the way), stop or hold; units with nothing to do go after the foes they see, and `RtsBattleAi` marches every other unit on its nearest foe when the map says so, the units thinking by turns once a second. The same orders at the same times play the same battle, so a test fights one with no view. A step costs about the units near each one rather than every pair: the battle asks which factions are hostile once (`are_foes()`, `RtsSides`), steps only the living units (`get_living_units()`), and files them by side and by where they stand (`RtsUnitGrid`) to find the foes a unit sees and the units it overlaps; a test holds a battle of 300 units to a budget per step. The module's minigame (`modules/rts/view/rts_battle_game.tscn`, setting `map`) shows the field scaled to the view, a selected unit that strikes from afar ringed with how far it reaches (`RtsBattleField.get_range_rings()`): click or drag a box to select (Shift adds), right click to attack or move, Attack-Move, Stop, Hold and All on the bar and on A, S, H and Tab, Ctrl and a digit to keep a group; with the keys or a gamepad, a cursor and accept or interact do the same, and on a touchscreen a tap does what fits where it lands (selects the player's unit, else sends the selection there), taking the nearest unit within half a fingertip, since a unit is far smaller than a finger (`get_pick_slack()`, `TouchTarget.reach`), and a finger that wanders less than a third of one still taps rather than drags a box (`RtsBattleField.get_drag_pixels()`). It tells `RtsEvents.battle_ended` and `foe_defeated`, and wins with the units of the player's side left as its score. How fast battle time and the cursor run are the game's `RtsSettings`.

Minigames: a minigame is a scene whose root extends `MiniGame` (`core/minigames/`), registered as a `MiniGameDefinition` content entry, whose settings the minigame checks with the rest of the content (`MiniGame.find_settings_problems()`). Any system starts one with `var result := await MiniGameHost.run(id, context)`; the host shows it above the world, pauses the world if the definition asks, blocks saving, plays the definition's music over the world's while it runs (`music_cue_id`), and runs the definition's `success_actions` or `failure_actions` through `GameRules` when it ends. A minigame never grants rewards itself, so the same minigame serves every caller. The first one is the fishing reel (`modules/lifesim/fishing/fishing_reel_minigame.gd`): when the game sets `FishingState.reel_minigame_id`, reeling in a biting fish plays it, and a win lands the fish. A `MiniGameStation` (`core/minigames/minigame_station.tscn`, which a game draws as children of its instance) runs one when the player uses it, or, given `choices`, lists several for the player to pick from (a `ChoiceMenu`, `MiniGameStation.choice_of()`): each by its `display_name` with its `description` and the player's best score under its `score_name`, marked once won, and locked while its `condition` does not hold, saying what it needs (`GameRules.describe()`). The host counts each win in the save (`MiniGameDefinition.get_wins()`) and keeps the best score in the profile, across saves (`get_best_score()`, a flag a `RecordData` can show). A definition's `score_goals` (Units Left 2, 3, 4) give that best score stars: the list and the pause menu's Challenges show them (★★☆) with the score the next one needs, the status line tells of each star earned, `MINIGAME_STARS <minigame> <count>` holds once the player has that many, and the content checks fail on goals that do not rise or that ask for more than the minigame can give (`MiniGame.get_best_possible_score()`: a battle, the units the player's side can field). The Challenges list them in their `order`, the open ones first. `MINIGAME_WON <minigame>` opens the next of a campaign once the one before it is won: Iron Banners' war table offers the Border Ford and then the Old Mill, its muster the Hill Pass and then the Raider Camp.

Translations: the core and each module translate their own player-visible text in `core/i18n/core.<locale>.po` and `modules/<module>/i18n/<module>.<locale>.po`; a game registers those catalogs with its own and translates only its own text. `tools/check_localization.js` checks every layer against its own catalogs. A list the player reads (the boons a run took, what a recipe needs) is joined with `GameText.list()` (`core/i18n/game_text.gd`), whose separator the core's catalog translates, so it reads "Gel, Ore" in English and "凝胶、矿石" in Chinese. See `docs/LOCALIZATION.md`.

Games and links: a game is a Godot project under `games/<id>/`, registered by its `game.json` (`id`, the `modules` it uses with every module they require, extra `addons`, its own `autoloads`, scripts of the game or of an addon it links under names the foundation does not use, and any `licensed_art`). Godot sees only files inside a project, so `node tools/link.js` links `tiamat/core/`, each listed module and each addon the game uses into it, as `res://tiamat/core`, `res://tiamat/modules/<module>` and `res://addons/<addon>` (directory junctions on Windows, relative symbolic links elsewhere). The links are Git-ignored and are the only copy a game has: nothing is copied, pinned or synchronized, and a game never edits the foundation through its links. It also writes the parts of the game's `project.godot` that follow from the manifests: the autoloads (the core's from `tiamat.json`, each listed module's, a module after the modules it requires, and the game's own from `game.json` `autoloads`), the translation catalogs, the addon plugins and the game's name in each language its own catalogs translate it to (`config/name_localized`, which names the window and a phone's app: MFarm is 麦田物语 in Chinese), and, when the game names none, the way a phone shows it (`window/handheld/orientation`): sensor landscape for a view wider than tall and sensor portrait otherwise, so the game turns the right way up whichever way the phone is held. In `export_presets.cfg` it gives the game a preset for every target in `tools/lib/targets.js` it lacks (from the new-game template) and sets what follows from the game in each: the export path, the application id `io.github.kukutx.<id>` of macOS and Android, the Android version code from `config/version`, the Android permissions the core and its modules declare in `tiamat.json` (`android_permissions`) and empty keystore fields, since signing keys come only from the environment. Everything else in those files belongs to the game, and validation fails when a committed file differs from what the tool writes. Run it after cloning and after changing a game's modules; every tool that runs Godot on a game links it first.

Shared pieces of a game: a player seen from above extends the core's `TopDownPlayer` (`core/player/top_down_player.gd`), which walks with the core's move controls (sped up or slowed by the `move_speed` stat), keeps what it reaches with in front of where it faces and stands still while the controls are held; the items module's `HotbarInput`, a child of the player, picks the hotbar's slot with the number keys, the game's next and previous actions and the mouse wheel (except a key or wheel turn the player bound to a control). An `InteractivePortal` (`core/world/interactive_portal.gd`) is a door or a way down the player uses on purpose, where a `ScenePortal` is walked into; Ember Depths' way into the depths is one that starts a run first. `GameClock.absolute_minute()` orders every moment of the world for durations and deadlines. The core's `WeatherOverlay`, which a game puts in its HUD (Farm1's `world_hud.tscn`), draws the day's weather over outdoor locations, and the core draws the licensed art a scene may lack (`LicensedArtSprite`, `LicensedTerrainLayer`, see `docs/LICENSED_ASSETS.md`). A `SheetAnimator` (`core/visual/sheet_animator.gd`) plays runs of a sprite sheet's cells through a sprite's region, looping or held on the last (a death): the combat module's creatures and the lifesim module's farm animals both animate with it. What a node in the world gives that the player's bag cannot hold waits on the ground by it, one pile until they take it, its count saved with the node (the items module's `OverflowDrop`, `modules/items/items/overflow_drop.gd`): a creature's loot and a mined rock's ore do. A chest in the world (the items module's `LootChest`, `modules/items/loot/`) holds a find of a `LootTable`: `picks` of its weighted `LootEntry` items, each from its level on (a depth, a floor) and at most once a find, and money that grows with the level; the player takes what the bag holds and the rest stays inside, a `locked` chest stays shut (an uncleared floor), a place laid out per run fills its chests from its own stream (`fill()`) and with a `persistent_id` what a chest still holds saves with the world, and `ItemsEvents.chest_opened` tells of the first opening. A place generated by depth spreads them with a `ChestSpread`: from `from_level` a floor holds one as often as `chance` says, a guarded floor always the `hoard` (`holds_chest()`, then `make()`): Ember Depths' floors hold one now and then and every guarded depth the Warden's Hoard, which its Treasure Hunter counts, and the lifesim mine's (`MineFloorTable.chests`, each floor's chest in its layout with its persistent id, so it is found once in a world, a guarded floor's sealed until its guardians fall) give Farm1's chests and Royal Hoards. A HUD is made of the core's lines (`core/ui/hud/`): a `PlaceLine` tells where and when (the place, what the scene adds with its `get_place_detail()`, such as a mine's floor or a dungeon's depth, the date and time, the weather), a `ControlsLine` names each control a game lists on the device in use with what it does (`InputPrompts.get_prompt()`: a single action, `move`, actions pressed together, or a prompt a module registers, such as the hotbar's number keys), and the items module's `HotbarLine` tells the slot in hand. A line of a game's own (Ember Depths' vitals and depth, Farm1's clock with the day's festival) extends `HudLine` or one of these, and every line is told again once at the end of a frame in which what it watches changed. A line that grows with what it tells (`shrinks_to_fit`, Farm1's clock) shrinks its text to its width, never below what a phone reads, and cuts the rest with an ellipsis rather than run over its neighbour (`ReadableText.fit_width()`, which any label can call, as Farm1's vitals and money do). A game's runtime smokes under `test/runtime/` extend `core/test/runtime_smoke.gd` by its path, which keeps their saves and profile apart, reads English text and fails the run when a check does.

A new game: `node tools/new_game.js --id <id> --name "<Game Name>"` copies `templates/new_game/` into `games/<id>/`, registers it with the modules `--modules <module>,...` names and every module they require (none without it) and links it; `--description "<One line>"` sets the line the title screen shows under its name. It is a small game that plays: the core's title screen as its main scene, a player (the core's `TopDownPlayer` with an `InteractionController`) and a HUD (place and time, status line, `SaveIndicator`, prompt, controls, pause menu, kept clear of a phone's camera by a `HudSafeArea`) of its own, two locations joined by `ScenePortal`s with a bed to sleep in, a game definition, an empty `GameSetup` module, a first hint and achievement with the triggers that show and unlock them, a unit test and a runtime smoke that walks through both portals, sleeps, saves and loads. Add modules to its `game.json` and run `node tools/link.js --game <id>`; the modules install themselves. A new module starts the same way: `node tools/new_module.js --id <id> [--requires <module>,...]` writes its `GameModule`, catalog and test under `modules/<id>/` and declares it in `tiamat.json` ([docs/MODULES.md](../docs/MODULES.md)). Validation creates such a game outside `games/` on every run and plays it through that smoke, so the core keeps working without any module, and a second one with every module, whose tests then run in a game that gives them no content, weather or settings of its own. A game can take `items` or `skills` alone, or any module with the modules it requires.

Tests: the core's tests live in `core/test/` and a module's in `modules/<module>/test/`; `node tools/link.js` lists them in each game's `.gutconfig.json`, so every game runs the tests of the foundation it links (the new-game check runs the core's alone). A foundation test builds its own content and makes it the only content with `ContentFixture.use()` (`core/test/content_fixture.gd`), since it may name no game's ids; the same file lets a test register a stat for its content (`add_stat()`) count the days by a calendar of its own whatever the game's is (`use_calendar()`), set the module settings it needs (`use_settings()`, with fixture vitals from `vital()`) and start a service on its own `GameDefinition` (`with_definition()`). `core/test/test_project_scripts_and_scenes.gd` loads every script and scene of the game it runs in, so a script no other test reaches still compiles in every game. A game's `test/unit/` keeps the tests of its own code, content, scenes and balance.
