# gamebase

The reusable foundation every game in this repository shares. Each game under `games/<id>/` holds its own content, scenes and rules in its `game/`; everything here is reused by later games, games of other genres and in-game minigames, and a fix here reaches every game at once.

```text
gamebase/core/                Genre-agnostic services: content, save, session, rules, settings,
                              input, audio, world travel, time, randomness, interactions, diagnostics
gamebase/modules/items/       Items, inventory, storage, shops, crafting, food buffs, building placement
gamebase/modules/skills/      Skill levels, experience and perks
gamebase/modules/combat/      Hostile creatures and enemy data               (requires items)
gamebase/modules/lifesim/     Farming, animals, fishing, forage, processing,   (requires items, skills, combat)
                              expansions, shipping, mining, calendar festivals
gamebase/modules/npc_social/  NPC actor, conversations, schedules,             (requires items, skills, lifesim)
                              relationships, heart events, memory
gamebase/modules/progression/ Quests, mail, collections, contracts,            (requires items, skills, lifesim, npc_social)
                              town projects, tool upgrades
gamebase/templates/new_game/  The project a new game starts from
gamebase/gamebase.json        Each module's required modules, addons and autoloads, the core's autoloads,
                              and the addons every game links
```

Dependency direction: a game may use `core/` and the modules its `game.json` lists; a module may use `core/` and the modules it requires in `gamebase.json`, and the requires form no cycle, so a game takes a module with only the modules below it; `core/` must not use a module, and nothing in `gamebase/` may use a game or name one of its ids (a value a game gives to `id` or to a `*_id` property in its data and scenes). `tools/check_layers.js` enforces this in validation for the foundation and for every game, with no exceptions list. A module gets game data through a slot the game fills: the mine floor table (`MineState.floor_table`, set in Farm1's `game/game_setup.gd`), a property set in the game's scene (the mine's entrance and floor spawn points, a housing's name and type, the shop stand's `shop`), a field of the game's data (what an animal eats), or `GameDefinition.ui_theme` for module menus. A game declares its input actions as `ControlAction` resources in `GameDefinition.controls`; the core adds the controls its own systems read (interact, quick save, quick load) unless the game replaces them. A module owns only its own vocabulary, such as the tool actions in `ItemData.ACTION_*`, and a game adds to it by registration (`ItemData.register_tool_action()`). A lower module never calls a higher one; the higher one plugs in instead: a shop sells another module's goods as `ShopOffer` resources in `ShopData.offers` (lifesim's `AnimalOffer`), a module adds what an NPC knows about its systems with `NpcContext.register_section()` (progression's quests and town projects), each module announces what happened in its systems on its own `<Module>Events` autoload (`NpcSocialEvents.npc_talked`, which quests count; `LifesimEvents.crop_harvested`, which a Farm1 trigger turns into farming experience), and content gates on another module's state through a `GameRules` condition (a recipe's `condition = "SKILL_LEVEL farming 2"`).

Each module wires itself into the core through registration, not through edits to `core/`: its `GameModule` class (`modules/items/items_module.gd` and the like) registers the module's kinds of content and their checks, rule keys, save sections, load steps, save blockers and new-game steps, and the core's `GameModules` autoload installs every module class the game links, so no game repeats that wiring. The game is a module of its own: `game/game_setup.gd` (`GameSetup`, a `GameModule`) installs what only the game knows (Farm1's starting animals, the mine floor table, its melee tool action). `game/game_definition.tres` (named by the `gamebase/game_definition` project setting) gives the start location, home, calendar, starting clock and items, the controls and the content packs.

Content: every piece of content is a `ContentEntry` resource of a kind its module defines (`ItemData.KIND` is `item`) and registers with `ContentDB.register_kind()`; a game lists its entries in `ContentPack` resources (`game/data/content.tres`) named by `GameDefinition.content`. Once every module has installed, `ContentDB` (`core/content/content_registry.gd`) indexes the packs and asks each entry for its problems (`find_problems()`: its fields and its references by id), each node of each location scene (`find_scene_problems()`, `get_persistent_keys()`), and each check a module registered for a whole kind (a quest chain without cycles); a problem fails validation. Code reads content through the class of its kind: `ItemData.find(&"berry")`, `QuestData.find_all()`, `WorldLocationData.find_current(get_tree())`; these read the active registry (`ContentRegistry.active`, the `ContentDB` autoload unless a test put its own content in place), so code never asks `ContentDB` for an entry itself. The running game's facts (start location, start items, controls) come from `GameDefinition.current()`.

Time: the core's `WorldClock` autoload (`core/time/game_clock.gd`) counts the day and the minute of the day. How the days group into seasons and weeks, how fast a minute passes, when night falls and when the player wakes or collapses is the game's `GameCalendar` (`GameDefinition.calendar`; four 28-day seasons when it sets none), read through `GameCalendar.current()`. The time conditions (`SEASON`, `DAY_OF_SEASON`, `WEEKDAY`) and every content check of a season name follow it, so a game of two ten-day seasons validates its content against those. `WorldClock.advance_until(condition, limit)` runs the clock on, each minute as if it passed, until a condition holds: to the evening, the next market day or a festival; while the player is up, the wait ends where they collapse. A location's `DayNightModulate` darkens it by the calendar's night, and a player who sleeps, collapses or is defeated after midnight wakes the same day.

Randomness: the core's `GameRandom` autoload (`core/random/game_random.gd`) holds the world's seed and gives each thing that rolls dice its own stream by key (`GameRandom.stream("forage:%d:%s" % [day, spawner])`), seeded by SHA-256 of the seed and the key. A stream (`GameRandomStream`) is the project's own xoshiro128** rather than the engine's generator, whose algorithm may change between engine versions, so the same world rolls the same weather, catches and mine floors on every load, platform and engine version, and a test pins an outcome by its seed. The seed is the `random` save section; a new game takes `GameDefinition.world_seed`, or a fresh seed when that is 0. Gameplay randomness never uses the global generator, which is left to cosmetic jitter such as a sound's pitch. The weather of a day is rolled from that seed with the odds the game gives per season (`GameDefinition.weather_odds`).

Stats: a number one system reads and others change (the energy a tool costs, how long a fish takes to bite, how hard an attack hits) is a stat of the core's `GameStats` autoload (`core/stats/game_stats.gd`). The module or game that reads a stat registers it when it installs (lifesim registers `fishing_wait`; Farm1's `GameSetup` registers `move_speed` and `attack_damage`) and reads it through `GameStats.apply()` or `get_multiplier()`. What changes stats registers as a source: the items module's food buffs and the skills module's perks, both content with `multipliers` and `bonuses` by stat, which `ContentDB` checks against the registered stats. Skills are content too (`SkillData`): the game defines its skills, their levels and their perks, and grants experience for the module events it chooses with triggers.

Conditions and actions: content says when something is available and what it does with short text keys (`condition = "HAS_ITEM berry 3, !QUEST_COMPLETED first_harvest"`), parsed by `core/rules/game_query.gd` and evaluated by the `GameRules` autoload. The core registers time, weather, location, flag and money keys; each module registers its own (`modules/items/items_rules.gd`, `modules/skills/skills_rules.gd`, `modules/lifesim/lifesim_rules.gd`, `modules/npc_social/npc_social_rules.gd`, `modules/progression/progression_rules.gd`) when it installs, with argument kinds of its own (`SkillsRules.ARG_SKILL`), a check of arguments that depend on each other (a level the named skill reaches) and, for a condition a menu shows, the requirement in words (`GameRules.describe()`: "Mining Lv3"). Every key content uses is checked at startup, so a typo fails validation. Whatever gates content on the state of the world is such a condition, in a `condition` field: a letter (`QUEST_COMPLETED first_harvest`), a heart event or an expansion (`PROJECT_COMPLETED garden_fund`), an NPC's route (`EVENT_ACTIVE spring_fair`). A system answers questions about its own state through its keys and never copies that state into world flags for others to read, so there is one source of truth and a misspelt id fails validation. A field stays only where the owning system plans with it, such as a crop's seasons, an event's date or a heart event's hearts (the order events play in). `WorldState` is the flag store for facts no system owns (`WORLD_FLAG`, set by dialogue or actions): booleans through `get_bool`, counters through `get_int`/`add_int`.

Triggers: what content does when something happens is a trigger (`core/rules/trigger_data.gd`, kind `trigger`): an `event`, a signal of an autoload written `<Autoload>.<signal>` (`LifesimEvents.crop_harvested`), a `condition` and `actions`, which the core's `GameTriggers` autoload runs when the event fires and the condition holds. The condition and actions see the event's arguments by name: `EVENT_ARG crop turnip` and `EVENT_ARG_AT_LEAST quantity 3` test them, an argument written `$name` passes one on (`ADD_SKILL_XP combat $combat_xp`), `repeat_per = quantity` runs the actions once per unit, and `once` fires a trigger once per world (an action that fails after others ran leaves it pending, and the next time the event fires it resumes there with the arguments of the event that set it off, each in its type, unless a content update changed its actions; a once trigger does not repeat, and its event declares only booleans, numbers and text, which a save keeps). A trigger's event and the arguments it reads are checked at startup, and the values an event passes are checked as written arguments are when it fires: a value that fails makes the condition false, whatever surrounds it, and runs none of the actions. What a save's restore or a new game's setup announces, until the player stands in the location, fires no trigger. Farm1 grants its skill experience this way (`game/data/triggers/`), so a game wires its modules together in data rather than in code.

Minigames: a minigame is a scene whose root extends `MiniGame` (`core/minigames/`), registered as a `MiniGameDefinition` content entry. Any system starts one with `var result := await MiniGameHost.run(id, context)`; the host shows it above the world, pauses the world if the definition asks, blocks saving, and runs the definition's `success_actions` or `failure_actions` through `GameRules` when it ends. A minigame never grants rewards itself, so the same minigame serves every caller. The first one is the fishing reel (`modules/lifesim/fishing/fishing_reel_minigame.gd`): when the game sets `FishingState.reel_minigame_id`, reeling in a biting fish plays it, and a win lands the fish.

Translations: the core and each module translate their own player-visible text in `core/i18n/core.<locale>.po` and `modules/<module>/i18n/<module>.<locale>.po`; a game registers those catalogs with its own and translates only its own text. `tools/check_localization.js` checks every layer against its own catalogs. See `docs/LOCALIZATION.md`.

Games and links: a game is a Godot project under `games/<id>/`, registered by its `game.json` (`id`, the `modules` it uses with every module they require, extra `addons`, its own `autoloads`, scripts of the game or of an addon it links under names the foundation does not use, and any `licensed_art`). Godot sees only files inside a project, so `node tools/link.js` links `gamebase/core/`, each listed module and each addon the game uses into it, as `res://gamebase/core`, `res://gamebase/modules/<module>` and `res://addons/<addon>` (directory junctions on Windows, relative symbolic links elsewhere). The links are Git-ignored and are the only copy a game has: nothing is copied, pinned or synchronized, and a game never edits the foundation through its links. It also writes the parts of the game's `project.godot` that follow from the manifests: the autoloads (the core's from `gamebase.json`, each listed module's, a module after the modules it requires, and the game's own from `game.json` `autoloads`), the translation catalogs and the addon plugins; everything else in `project.godot` belongs to the game, and validation fails when a committed `project.godot` differs from what the tool writes. Run it after cloning and after changing a game's modules; every tool that runs Godot on a game links it first.

A new game: `node tools/new_game.js --id <id> --name "<Game Name>"` copies `templates/new_game/` into `games/<id>/` (a game definition, an empty `GameSetup` module, a content pack with one start location and a runtime smoke), registers it with no module and links it. Add modules to its `game.json` and run `node tools/link.js --game <id>`; the modules install themselves. Validation creates such a game outside `games/` on every run and takes it through a new game, a save and a load, so the core keeps working without any module. A game can take `items` or `skills` alone, or any module with the modules it requires.

Tests: the core's tests live in `core/test/` and a module's in `modules/<module>/test/`; `node tools/link.js` lists them in each game's `.gutconfig.json`, so every game runs the tests of the foundation it links (the new-game check runs the core's alone). A foundation test builds its own content and makes it the only content with `ContentFixture.use()` (`core/test/content_fixture.gd`), since it may name no game's ids; the same file lets a test register a stat for its content (`add_stat()`) and start a service on its own `GameDefinition` (`with_definition()`). A game's `test/unit/` keeps the tests of its own code, content, scenes and balance.
