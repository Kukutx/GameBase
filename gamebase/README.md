# gamebase

The reusable foundation every game in this repository shares. Each game under `games/<id>/` holds its own content, scenes and rules in its `game/`; everything here is reused by later games, games of other genres and in-game minigames, and a fix here reaches every game at once.

```text
gamebase/core/                Genre-agnostic services: content, save, session, rules, settings,
                              input, audio, world travel, depth tracks, time, randomness, triggers,
                              player vitals, player profile, playthroughs and what carries over, interactions,
                              state machines, node pools, screen shake, diagnostics, and the
                              title, pause and settings menus
gamebase/modules/items/       Items, inventory, money, storage, shops, crafting, food buffs, building placement
gamebase/modules/skills/      Skill levels, experience and perks
gamebase/modules/combat/      Health, damage and factions, hurtboxes,        (requires items)
                              hostile creatures, enemy data, the melee
                              attack, enemy tiers by depth and the player's defeat
gamebase/modules/lifesim/     Farming, animals, fishing, forage, processing,   (requires items, skills, combat)
                              expansions, shipping, mining, calendar festivals, staying up late
gamebase/modules/npc_social/  NPC actor, conversations and their balloon,      (requires items, skills, lifesim)
                              schedules, relationships, heart events, memory
gamebase/modules/progression/ Quests, mail, collections, contracts,            (requires items, skills, combat, lifesim, npc_social)
                              town projects, tool upgrades
gamebase/modules/roguelite/   Runs: their count, outcomes, run-long values and random streams
gamebase/templates/new_game/  The project a new game starts from
gamebase/gamebase.json        Each module's required modules, addons and autoloads, the core's autoloads,
                              and the addons every game links
```

Dependency direction: a game may use `core/` and the modules its `game.json` lists; a module may use `core/` and the modules it requires in `gamebase.json`, and the requires form no cycle, so a game takes a module with only the modules below it; `core/` must not use a module, and nothing in `gamebase/` may use a game or name one of its ids (a value a game gives to `id` or to a `*_id` property in its data and scenes). `tools/check_layers.js` enforces this in validation for the foundation and for every game, with no exceptions list. A module gets game data through a slot the game fills: the mine floor table (`MineState.floor_table`, set in Farm1's `game/game_setup.gd`), a property set in the game's scene (the mine's entrance and floor spawn points, a housing's name and type, the shop stand's `shop`), a field of the game's data (what an animal eats). A game declares its input actions as `ControlAction` resources in `GameDefinition.controls`; the core adds the controls its own systems read (the four moves a `TopDownPlayer` walks with, `core/input/controls/move_*.tres`, interact, quick save and quick load) unless the game lists them to place or replace them; `InputPrompts.get_move_prompt()` shows the moves on the device in use. A module owns only its own vocabulary, such as the tool actions it responds to (`FarmPlot.TILL_ACTION`, `MeleeAttack.TOOL_ACTION`): the items module knows a tool's action only as a name, and whoever handles one registers it (`ItemData.register_tool_action()`), a game for its own actions too. A lower module never calls a higher one; the higher one plugs in instead: a shop sells another module's goods as `ShopOffer` resources in `ShopData.offers` (lifesim's `AnimalOffer`), a module adds what an NPC knows about its systems with `NpcContext.register_section()` (progression's quests and town projects), each module announces what happened in its systems on its own `<Module>Events` autoload (`NpcSocialEvents.npc_talked`, which quests count; `LifesimEvents.crop_harvested`, which a Farm1 trigger turns into farming experience), and content gates on another module's state through a `GameRules` condition (a recipe's `condition = "SKILL_LEVEL farming 2"`).

Each module wires itself into the core through registration, not through edits to `core/`: its `GameModule` class (`modules/items/items_module.gd` and the like) registers the module's kinds of content and their checks, rule keys, save sections, load steps, save blockers and new-game steps, and the core's `GameModules` autoload installs every module class the game links, so no game repeats that wiring. The game is a module of its own: `game/game_setup.gd` (`GameSetup`, a `GameModule`) installs what only the game knows (Farm1's starting animals and mine floor table, Ember Depths' save blocker in the depths). `game/game_definition.tres` (named by the `gamebase/game_definition` project setting) gives the start location, home, calendar, starting clock and items, the controls and the content packs.

Content: every piece of content is a `ContentEntry` resource of a kind its module defines (`ItemData.KIND` is `item`) and registers with `ContentDB.register_kind()`; a game lists its entries in `ContentPack` resources (`game/data/content.tres`) named by `GameDefinition.content`. Once every module has installed, `ContentDB` (`core/content/content_registry.gd`) indexes the packs and asks each entry for its problems (`find_problems()`: its fields and its references by id), each node of each location scene (`find_scene_problems()`, `get_persistent_keys()`), and each check a module registered for a whole kind (a quest chain without cycles); a problem fails validation. A release build only indexes: its content passed these checks before the export, so it takes what they proved (a location's spawn points) as given (`checked_before_export`). Code reads content through the class of its kind: `ItemData.find(&"berry")`, `QuestData.find_all()`, `WorldLocationData.find_current(get_tree())`; these read the active registry (`ContentRegistry.active`, the `ContentDB` autoload unless a test put its own content in place), so code never asks `ContentDB` for an entry itself. The running game's facts (start location, controls, calendar) come from `GameDefinition.current()`. What a game sets for a module is a `ModuleSettings` resource of that module's own in `GameDefinition.module_settings` (`ItemsSettings`: the starting money and items; `CombatSettings`: the vital hits take and what a defeat costs; `LifesimSettings`: the vital work spends and how late the player may stay up), which the module reads with `GameDefinition.current().get_settings()`, usually through the settings' own `current()` (`ItemsSettings.current()`); a game that lists none of a kind gets its defaults. A module registers its kind with `ContentDB.register_settings()`, so what is wrong with the settings a game runs with, listed or default (an id that names nothing), fails validation as a content problem does.

Time: the core's `WorldClock` autoload (`core/time/game_clock.gd`) counts the day and the minute of the day. How the days group into seasons and weeks, how fast a minute passes, when night falls and when the player wakes is the game's `GameCalendar` (`GameDefinition.calendar`; four 28-day seasons when it sets none), read through `GameCalendar.current()`. The time conditions (`SEASON`, `DAY_OF_SEASON`, `WEEKDAY`) and every content check of a season name follow it, so a game of two ten-day seasons validates its content against those. `WorldClock.advance_until(condition, limit)` runs the clock on, each minute as if it passed, until a condition holds: to the evening, the next market day or a festival; a wait also ends at a minute a module stops it at (`WorldClock.register_wait_stop()`: the late night lifesim sends a player who is still up home at). A location's `DayNightModulate` darkens it by the calendar's night, and a player who sleeps or passes out after midnight wakes the same day. A calendar whose minutes last no time (`real_seconds_per_game_minute = 0`, Ember Depths) stands still until something moves it, such as a rest or a defeat. `GameCalendar.get_date_text()` gives a day as the player reads it ("Spring 3", "Spring 3, Year 2", or "Day 31" for a calendar of one season); the HUD clock, the save slots and resting use it.

Randomness: the core's `GameRandom` autoload (`core/random/game_random.gd`) holds the world's seed and gives each thing that rolls dice its own stream by key (`GameRandom.stream("forage:%d:%s:%s" % [day, spawner_id, location_id])`), seeded by SHA-256 of the seed and the key. A stream (`GameRandomStream`) is the project's own xoshiro128** rather than the engine's generator, whose algorithm may change between engine versions, so the same world rolls the same weather, catches and mine floors on every load, platform and engine version, and a test pins an outcome by its seed. The seed is the `random` save section; a new game takes `GameDefinition.world_seed`, or a fresh seed when that is 0. Gameplay randomness never uses the global generator, which is left to cosmetic jitter such as a sound's pitch. The weather of a day is rolled from that seed with the chances the game gives each of its weathers per season (`GameDefinition.weather_odds`, in the order they are listed); a day they give no other weather has `GameDefinition.clear_weather_id`. Each weather is content (`WeatherData`, kind `weather`): its name, whether it waters what grows outside, and how the `WeatherOverlay` shows it (a tint, rain or snow, lightning). A fish, an NPC's route and `WEATHER storm` name weather by id (`WeatherState.get_weather_id(day)`), and a game that names no clear weather has none.

Stats: a number one system reads and others change (the energy a tool costs, how long a fish takes to bite, how hard an attack hits) is a stat of the core's `GameStats` autoload (`core/stats/game_stats.gd`). The module or game that reads a stat registers it when it installs (the core registers `move_speed`, which a `TopDownPlayer` walks by; lifesim `fishing_wait`, combat `attack_damage` and `attack_cost`) and reads it through `GameStats.apply()` or `get_multiplier()`. What changes stats registers as a source: the items module's food buffs and the skills module's perks, both content with `multipliers` and `bonuses` by stat, which `ContentDB` checks against the registered stats. Skills are content too (`SkillData`): the game defines its skills, their levels and their perks, and grants experience for the module events it chooses with triggers.

Conditions and actions: content says when something is available and what it does with short text keys (`condition = "HAS_ITEM berry 3, !QUEST_COMPLETED first_harvest"`), parsed by `core/rules/game_query.gd` and evaluated by the `GameRules` autoload. The core registers time, weather, location, flag and vital keys; each module registers its own (`modules/items/items_rules.gd`, `modules/skills/skills_rules.gd`, `modules/lifesim/lifesim_rules.gd`, `modules/npc_social/npc_social_rules.gd`, `modules/progression/progression_rules.gd`) when it installs, with argument kinds of its own (`SkillsRules.ARG_SKILL`), a check of arguments that depend on each other (a level the named skill reaches) and, for a condition a menu shows, the requirement in words (`GameRules.describe()`: "Mining Lv3"). Every key content uses is checked at startup, so a typo fails validation. Whatever gates content on the state of the world is such a condition, in a `condition` field: a letter (`QUEST_COMPLETED first_harvest`), a heart event or an expansion (`PROJECT_COMPLETED garden_fund`), an NPC's route (`EVENT_ACTIVE spring_fair`). A system answers questions about its own state through its keys and never copies that state into world flags for others to read, so there is one source of truth and a misspelt id fails validation. A field stays only where the owning system plans with it, such as a crop's seasons, an event's date or a heart event's hearts (the order events play in). `WorldState` is the flag store for facts no system owns (`WORLD_FLAG`, set by dialogue or actions): booleans through `get_bool`, counters through `get_int`/`add_int`.

Events: content listens to what happens through events (`core/rules/game_event.gd`), each a signal of an autoload written `<Autoload>.<signal>` (`LifesimEvents.crop_harvested`), whose arguments it reads by name; `GameEventListener` connects code to one the same way. An argument named `<kind>_id` (or ends in `_<kind>_id`) holds an id of that kind of content (`crop_id`, `mining_node_id`, `result_item_id`), so the ids content compares it with and the keys it passes it to are checked at startup. [docs/reference/events.md](../docs/reference/events.md) lists every event of the foundation.

Triggers: what content does when something happens is a trigger (`core/rules/trigger_data.gd`, kind `trigger`): an `event`, a `condition` and `actions`, which the core's `GameTriggers` autoload runs when the event fires and the condition holds. The condition and actions see the event's arguments by name: `EVENT_ARG crop_id turnip` and `EVENT_ARG_AT_LEAST quantity 3` test them, an argument written `$name` passes one on (`ADD_SKILL_XP combat $combat_xp`), `repeat_per = quantity` runs the actions once per unit, and `once` fires a trigger once per world (an action that fails after others ran leaves it pending, and the next time the event fires it resumes there with the arguments of the event that set it off, each in its type, unless a content update changed its actions; a once trigger does not repeat, and its event declares only booleans, numbers and text, which a save keeps). A trigger's event and the arguments it reads are checked at startup, and the values an event passes are checked as written arguments are when it fires: a value that fails makes the condition false, whatever surrounds it, and runs none of the actions. What a save's restore or a new game's setup announces, until the player stands in the location, fires no trigger. Farm1 grants its skill experience this way (`game/data/triggers/`), so a game wires its modules together in data rather than in code.

Quests: a quest (`modules/progression/quests/quest_data.gd`) asks for one or more `objectives` (`QuestObjective`), each counted from an event of any module the way a trigger listens to one: its `event`, a `condition` on the event's arguments (`EVENT_ARG crop_id turnip`, or `ITEM_TAG $item_id fish` for every item tagged fish), `count_per` an integer argument (`quantity`) and the `required_amount`; with a `measure`, an autoload's method returning an int (`MineState.get_deepest_floor`), it follows that number instead of counting. `QuestState` listens only to the events of the active quests' objectives, pays the reward once every objective is met and saves each objective's progress, so no quest code names the modules whose events its quests count.

Player profile: the core's `GameProfile` autoload (`core/profile/game_profile.gd`) keeps what outlives every save of a game in `user://profile.json`: the achievements the player unlocked (`AchievementData`, a kind of content) and profile flags, booleans and counters as `WorldState` keeps a world's. A new game, a load or a deleted slot leave it alone. Reading the file keeps only what is well formed and names current content; a change that could not be written is written with the next one or at quit, and the player is told once. Content reaches it through rule keys (`UNLOCK_ACHIEVEMENT`, `ACHIEVEMENT_UNLOCKED`, `SET_PROFILE_FLAG`, `ADD_PROFILE_FLAG`, `PROFILE_FLAG`, `PROFILE_FLAG_AT_LEAST`), usually from triggers: Farm1 unlocks Green Thumb on its first harvest and counts every save's crops toward Seasoned Farmer with a trigger on `GameProfile.flag_changed`. A storefront's achievements follow `GameProfile.achievement_unlocked`. A game's HUD shows the unlock, as every toast, on a `StatusLine` (`core/events/status_line.gd`), which shows messages sent together one after another rather than only the last.

Playthroughs and what carries over: the core's `Playthrough` autoload (`core/playthrough/playthrough_service.gd`) numbers the playthrough a save belongs to, and `PLAYTHROUGH_AT_LEAST` lets content ask for it. A game lists what a new playthrough carries over in `GameDefinition.inheritance`, each an `InheritanceRule` with a key: `WorldValueInheritance` (world values under some prefixes), the items module's `MoneyInheritance` (a share of the money) and `ItemInheritance` (items with some tags) and the skills module's `SkillInheritance` (a share of each skill's experience). `Playthrough.start_next()` takes each rule's part of the game as it is and starts a new game that begins with it. A sequel carries a game over the same way: `write_legacy()` writes the parts by key to `user://legacy.json`, and the sequel reads it (`PlaythroughService.find_legacy("<the game's name>")`) and starts from it (`start_from_legacy()`), each of its rules taking the part with its key.

Depths and runs: a place that goes down depth by depth keeps its depth and the deepest one reached in a `DepthTrack` (`core/world/depth_track.gd`), in the world under its key, with an optional bottom, checkpoints to return to and a random stream per depth: Farm1's mine (`MineState`) and Ember Depths' depths both use one. The roguelite module's `RunState` (`modules/roguelite/runs/run_service.gd`) counts the runs a world started, keeps values that last one run and a random stream per run, and ends a run with an outcome: back at camp (the game says so), defeated, or abandoned when the player passes out for another cause (lifesim's late night), a load, a new game or the title takes them out of play (passing out saves what the run brought). While a run goes on the game cannot be saved, unless the game lets it (`RunState.blocks_saves`); `RunState.run_started` and `run_ended` are events triggers follow, and `RUN_ACTIVE` and `RUNS_AT_LEAST` are its rule keys.

Places and travel: every place the player can be is a `WorldLocationData` (kind `location`) with its scene, spawn points and an optional region (`RegionData`, kind `region`). `WorldTravel.travel_to(location_id, spawn_id, params)` changes the scene behind the core's fade (`Transition`), and `await WorldTravel.go_to(...)` also waits until the player stands there. The `params` a travel carries (the floor to open, the door used) are the place's to read with `WorldTravel.get_params()` from its `_ready()` on. Arriving in a location of another region fires `WorldTravel.region_changed` (a load enters the region of its scene too), and `REGION valley` asks where the player is; a load and the title forget the last travel's parameters. A cutscene covers the screen without changing the scene with `await Transition.cover(self)` and clears it with `await Transition.uncover()`; a travel under the cover leaves the screen covered, the cover ends with the cutscene node if it is freed first, and a load or the title gives it back. `await Transition.wait_until_clear()` waits until no change, cover or fade shows. A wait that has to wait resumes on a later frame rather than inside a signal, so what waited may free nodes or travel on at once.

Vitals and money: what the player counts down and refills (health, energy, mana) is content, each a `VitalData` (kind `vital`) with its name, its maximum and whether a night's sleep refills it, and the core's `Vitals` autoload (`core/player/player_vitals.gd`) holds the player's. Work and attacks spend a vital (`try_spend()` tells the player when there is not enough), food and rest restore it (an item's `restores`, by vital id, used with `InventoryState.consume()`), and `depleted` fires when one reaches 0. The core gives no vital a meaning: the module that uses one names it in its settings, so a game that leaves `LifesimSettings.energy_vital_id` empty has free tools, and one without `CombatSettings.health_vital_id` has hits that hurt nothing. `VITAL_AT_LEAST` and `RESTORE_VITAL` are their rule keys and `Vitals.describe_all()` gives them as a HUD shows them. Money is the items module's `Wallet` (`modules/items/wallet/`), with `MONEY_AT_LEAST` and `ADD_MONEY`. A module that knocks the player out calls `await GameSession.pass_out(cause, recover)`: `GameSession.passing_out` fires, the player's activities end, `recover` restores or takes what the cause does (before the night's payouts arrive), the clock moves to the next morning, and the player wakes at home and the game saves (`passed_out`). Combat's defeat is one cause, lifesim's late night (`LateNight`) another: a player still up at `LifesimSettings.late_night_minute` wakes with `late_night_energy_percent` of their energy and `LifesimEvents.stayed_up_late` follows.

Combat: what every fight shares lives in the combat module's `damage/`: `Health` (between 0 and a maximum, `depleted` at 0), `Damage` (an amount, the faction it comes from, its source and its knockback) and `FactionData` (any two factions fight unless one lists the other among its `allies`; an id alone names a side, such as `player` and `monsters`). In real time an actor is hit through its `Hurtbox` (`modules/combat/combat/hurtbox.gd`), which takes damage of a hostile faction only, flashes the actor, pushes it back and then takes no hit for `invincible_seconds`; the player's `PlayerHurtbox` drains the game's health vital (`CombatSettings.health_vital_id`), staggers the player while the push carries them (`TopDownPlayer.stagger()`) and shakes the screen with the core's `ScreenShake` (`core/camera/screen_shake.gd`, which does nothing with reduced motion). `MeleeAttack`, a child of the player, swings the weapon selected in the hotbar (an item whose tool action is `attack`) at every hostile hurtbox it overlaps, for the weapon's power changed by `attack_damage`, spends its `cost` (changed by `attack_cost`) of the attack vital (`CombatSettings.attack_vital_id`; none, and swings are free), draws its arc (`SwingEffect`, kept in a `NodePool`) and swings again after `cooldown_seconds`. A `HostileCreature` runs on a `StateMachine` (idle, chase, hurt, defeated) and strikes the player's hurtbox. `CombatEvents.attack_swung`, `enemy_hurt`, `player_hurt` and `enemy_defeated` are events a game maps to sounds. A place generated by depth lists its enemies as `EnemyTier` entries, each from its minimum depth on: Farm1's mine floors and Ember Depths' floors. When the health vital runs out (or a load or another cause of passing out leaves it empty), the combat module's `PlayerDefeat` (`modules/combat/defeat/`) passes the player out with the cause `defeat`: they wake at home with every vital full and `CombatSettings.defeat_money_loss_percent` of their money gone, and `CombatEvents.player_defeated` says what it cost.

Menus: the core ships the title screen, the pause menu and the settings menu (`core/ui/`). A game makes `res://gamebase/core/ui/title_screen.tscn` its main scene, and the title takes the game's name and description from `project.godot`. Every menu, the core's and the modules', draws with the project theme a game sets in `project.godot` (`gui/theme/custom`); a new game starts on the core's `core/ui/default_theme.tres`. Text shows in the font the core ships, Noto Sans SC (`core/ui/fonts/`), which `GameSettings` makes the font of the engine's default theme (`use_font()`), so every text shows in it unless a game's theme names another: it holds Latin, Chinese punctuation, the characters of GB 2312 and every character the repository's text uses, cut down by `node tools/subset_font.js`, since a web build has no system fonts to fall back on; the core's `test_theme_font` checks every translation a game registers against the font it shows in. A game puts the pause menu (`core/ui/pause_menu.tscn`) in its HUD; it saves, loads (quick load too, after asking), opens the settings, returns to the main scene and quits, and opens when the window loses focus. The settings (`GameSettings`) cover volume (the core adds the Music and Sounds buses a game's bus layout lacks), display, autosave, how fast dialogue types out (`get_seconds_per_character()`), language, accessibility and the rebinding of each control's key and gamepad button; a game without weather does not show the weather effects toggle. The items module's shop menu sells, one at a time, every item the inventory holds that has a price.

Saves: the core's `SaveManager` keeps three slots, each a save, a backup and an interrupted save it can recover from. The title screen shows what a slot holds: the date and time, where the player stands, the time played (`GameSession.get_play_seconds()`, the save's `session` section) and what the modules and the game add with `SaveManager.register_slot_detail()` (the items module's money, Ember Depths' deepest depth). `AutoSave` saves every few minutes, after each travel and when the window closes; a game puts a `SaveIndicator` (`core/ui/save_indicator.gd`) in its HUD to show that it did, and an autosave that fails is a toast with the reason. Every message of a save or a load is a sentence for the player, and the log names the file that could not be written.

Controls and pause: the core's `InputLock` autoload (`core/input/input_lock.gd`) holds the player's controls and the world's pause by reason. The core's and the modules' menus extend the core's `MenuLayer` (`core/ui/menu_layer.gd`), which takes `InputLock.lock(&"shop_menu", true, self)` while it shows, closes on `ui_cancel` and is found by its id as a group; a conversation (the npc_social module's `DialogueBalloon`, along the bottom of the view whatever its size) pauses the world too, so the clock stands still while the player reads, a fishing cast takes a lock that does not pause, and the player acts only while nothing holds a lock. Locks add up, so a menu that closes while a minigame runs leaves the world paused, and a lock with an owner node is given back when the owner leaves the tree. They also stack as modes: the latest lock is on top, and a menu or minigame reads its keys only while its own lock is (`InputLock.is_top(self)`), so a menu opened over a minigame takes the keys and `ui_cancel` closes only the topmost menu. Nothing else sets `SceneTree.paused`, which `tools/check_code.js` checks with the other code guardrails: a script has at most 500 lines (a test at most 1000), nothing the game ships loads a resource from `user://` or saves one at runtime, and player data is read as JSON, never with `ConfigFile` or `str_to_var()`, whose text can name a resource to load or an object to build.

Building blocks: a `StateMachine` (`core/flow/state_machine.gd`) runs named states, each with what it does on entering, on every update and on leaving, for a creature's idle, chase and attack or a door's shut, opening and open; a state changes it with `change()`, and a change asked for during another follows it. `NodeRegistry` (`core/nodes/node_registry.gd`) finds a node by an id it registered under (a boss a cutscene speaks to, a door a switch opens) until it leaves the tree. `NodePool` (`core/nodes/node_pool.gd`) keeps instances of a scene (hit sparks, damage numbers) to use again rather than make and free them each time; an instance that must start over resets itself in a `reuse()` method.

Minigames: a minigame is a scene whose root extends `MiniGame` (`core/minigames/`), registered as a `MiniGameDefinition` content entry. Any system starts one with `var result := await MiniGameHost.run(id, context)`; the host shows it above the world, pauses the world if the definition asks, blocks saving, and runs the definition's `success_actions` or `failure_actions` through `GameRules` when it ends. A minigame never grants rewards itself, so the same minigame serves every caller. The first one is the fishing reel (`modules/lifesim/fishing/fishing_reel_minigame.gd`): when the game sets `FishingState.reel_minigame_id`, reeling in a biting fish plays it, and a win lands the fish.

Translations: the core and each module translate their own player-visible text in `core/i18n/core.<locale>.po` and `modules/<module>/i18n/<module>.<locale>.po`; a game registers those catalogs with its own and translates only its own text. `tools/check_localization.js` checks every layer against its own catalogs. See `docs/LOCALIZATION.md`.

Games and links: a game is a Godot project under `games/<id>/`, registered by its `game.json` (`id`, the `modules` it uses with every module they require, extra `addons`, its own `autoloads`, scripts of the game or of an addon it links under names the foundation does not use, and any `licensed_art`). Godot sees only files inside a project, so `node tools/link.js` links `gamebase/core/`, each listed module and each addon the game uses into it, as `res://gamebase/core`, `res://gamebase/modules/<module>` and `res://addons/<addon>` (directory junctions on Windows, relative symbolic links elsewhere). The links are Git-ignored and are the only copy a game has: nothing is copied, pinned or synchronized, and a game never edits the foundation through its links. It also writes the parts of the game's `project.godot` that follow from the manifests: the autoloads (the core's from `gamebase.json`, each listed module's, a module after the modules it requires, and the game's own from `game.json` `autoloads`), the translation catalogs and the addon plugins; everything else in `project.godot` belongs to the game, and validation fails when a committed `project.godot` differs from what the tool writes. Run it after cloning and after changing a game's modules; every tool that runs Godot on a game links it first.

Shared pieces of a game: a player seen from above extends the core's `TopDownPlayer` (`core/player/top_down_player.gd`), which walks with the core's move controls (sped up or slowed by the `move_speed` stat), keeps what it reaches with in front of where it faces and stands still while the controls are held; the items module's `HotbarInput`, a child of the player, picks the hotbar's slot with the number keys (except one the player bound to a control), the game's next and previous actions and the mouse wheel. An `InteractivePortal` (`core/world/interactive_portal.gd`) is a door or a way down the player uses on purpose, where a `ScenePortal` is walked into; Ember Depths' way into the depths is one that starts a run first. `GameClock.absolute_minute()` orders every moment of the world for durations and deadlines. The core's `WeatherOverlay`, which a game puts in its HUD (Farm1's `world_hud.tscn`), draws the day's weather over outdoor locations, and the core draws the licensed art a scene may lack (`LicensedArtSprite`, `LicensedTerrainLayer`, see `docs/LICENSED_ASSETS.md`). A game's runtime smokes under `test/runtime/` extend `core/test/runtime_smoke.gd` by its path, which keeps their saves and profile apart, reads English text and fails the run when a check does.

A new game: `node tools/new_game.js --id <id> --name "<Game Name>"` copies `templates/new_game/` into `games/<id>/`, registers it with no module and links it; `--description "<One line>"` sets the line the title screen shows under its name. It is a small game that plays: the core's title screen as its main scene, a player (the core's `TopDownPlayer` with an `InteractionController`) and a HUD (place and time, status line, `SaveIndicator`, prompt, controls, pause menu) of its own, two locations joined by `ScenePortal`s with a bed to sleep in, a game definition, an empty `GameSetup` module, a unit test and a runtime smoke that walks through both portals, sleeps, saves and loads. Add modules to its `game.json` and run `node tools/link.js --game <id>`; the modules install themselves. Validation creates such a game outside `games/` on every run and plays it through that smoke, so the core keeps working without any module. A game can take `items` or `skills` alone, or any module with the modules it requires.

Tests: the core's tests live in `core/test/` and a module's in `modules/<module>/test/`; `node tools/link.js` lists them in each game's `.gutconfig.json`, so every game runs the tests of the foundation it links (the new-game check runs the core's alone). A foundation test builds its own content and makes it the only content with `ContentFixture.use()` (`core/test/content_fixture.gd`), since it may name no game's ids; the same file lets a test register a stat for its content (`add_stat()`) count the days by a calendar of its own whatever the game's is (`use_calendar()`), set the module settings it needs (`use_settings()`, with fixture vitals from `vital()`) and start a service on its own `GameDefinition` (`with_definition()`). `core/test/test_project_scripts_and_scenes.gd` loads every script and scene of the game it runs in, so a script no other test reaches still compiles in every game. A game's `test/unit/` keeps the tests of its own code, content, scenes and balance.
