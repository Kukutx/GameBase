# gamebase

The reusable foundation every game in this repository shares. Each game under `games/<id>/` holds its own content, scenes and rules in its `game/`; everything here is reused by later games, games of other genres and in-game minigames, and a fix here reaches every game at once.

```text
gamebase/core/                Genre-agnostic services: content, save, session, rules, settings,
                              input, audio, world travel, time, interactions, diagnostics
gamebase/modules/items/       Items, inventory, storage, shops, crafting, food buffs, building placement
gamebase/modules/skills/      Skill levels, experience and perks
gamebase/modules/combat/      Hostile creatures and enemy data               (requires items)
gamebase/modules/lifesim/     Farming, animals, fishing, forage, processing,   (requires items, skills, combat)
                              expansions, shipping, mining, calendar festivals
gamebase/modules/npc_social/  NPC actor, conversations, schedules,             (requires items, skills, lifesim)
                              relationships, heart events, memory
gamebase/modules/progression/ Quests, mail, collections, contracts,            (requires items, skills, lifesim, npc_social)
                              town projects, tool upgrades
gamebase/templates/new_game/  The project a new game starts from
gamebase/gamebase.json        Each module's required modules, addons and autoloads, the core's autoloads,
                              and the addons every game links
```

Dependency direction: a game may use `core/` and the modules its `game.json` lists; a module may use `core/` and the modules it requires in `gamebase.json`, and the requires form no cycle, so a game takes a module with only the modules below it; `core/` must not use a module, and nothing in `gamebase/` may use a game or name one of its ids (a value a game gives to `id` or to a `*_id` property in its data and scenes). `tools/check_layers.js` enforces this in validation for the foundation and for every game, with no exceptions list. The `ContentDB` autoload is the one sanctioned crossing: its script lives in the game but extends the core `ContentRegistry`, and the check verifies that every method called on it exists. A module gets game data through a slot the game fills: the mine floor table (`MineState.floor_table`, set in Farm1's `game/game_setup.gd`), a property set in the game's scene (the mine's entrance and floor spawn points, a housing's name and type, the shop stand's `shop`), a field of the game's data (what an animal eats), or `GameDefinition.ui_theme` for module menus. A game declares its input actions as `ControlAction` resources in `GameDefinition.controls`; the core adds the controls its own systems read (interact, quick save, quick load) unless the game replaces them. A module owns only its own vocabulary, such as the tool actions in `ItemData.ACTION_*`. A lower module never calls a higher one; the higher one plugs in instead: a shop sells another module's goods as `ShopOffer` resources in `ShopData.offers` (lifesim's `AnimalOffer`), a module adds what an NPC knows about its systems with `NpcContext.register_section()` (progression's quests and town projects), modules announce what happened on the core's `GameEvents` signals (`npc_talked`, which quests count), and content gates on another module's state through a `GameRules` condition (a recipe's `condition = "SKILL_LEVEL farming 2"`).

Each module wires itself into the core through registration, not through edits to `core/`: its `GameModule` class (`modules/items/items_module.gd` and the like) registers the module's rule keys, save sections, load steps, save blockers and new-game steps, and the core's `GameModules` autoload installs every module class the game links, so no game repeats that wiring. The game's `game/game_setup.gd` keeps what only the game knows (Farm1's starting animals and the mine floor table), `game/content/game_content_database.gd` extends the generic `ContentRegistry` with the kinds of content its modules define, and `game/game_definition.tres` (named by the `gamebase/game_definition` project setting) gives the start location, home, starting clock and items.

Conditions and actions: content says when something is available and what it does with short text keys (`condition = "HAS_ITEM berry 3, !QUEST_COMPLETED first_harvest"`), parsed by `core/rules/game_query.gd` and evaluated by the `GameRules` autoload. The core registers time, weather, location, flag and money keys; each module registers its own (`modules/items/items_rules.gd`, `modules/skills/skills_rules.gd`, `modules/progression/progression_rules.gd`, `modules/npc_social/npc_social_rules.gd`) when it installs, with argument kinds of its own (`SkillsRules.ARG_SKILL`) and, for a condition a menu shows, the requirement in words (`GameRules.describe()`: "Mining Lv3"). Every key content uses is checked at startup, so a typo fails validation. `WorldState` is the flag store: booleans through `get_bool`, counters through `get_int`/`add_int`.

Minigames: a minigame is a scene whose root extends `MiniGame` (`core/minigames/`), registered as a `MiniGameDefinition` content entry. Any system starts one with `var result := await MiniGameHost.run(id, context)`; the host shows it above the world, pauses the world if the definition asks, blocks saving, and runs the definition's `success_actions` or `failure_actions` through `GameRules` when it ends. A minigame never grants rewards itself, so the same minigame serves every caller. The first one is the fishing reel (`modules/lifesim/fishing/fishing_reel_minigame.gd`): when the game sets `FishingState.reel_minigame_id`, reeling in a biting fish plays it, and a win lands the fish.

Translations: the core and each module translate their own player-visible text in `core/i18n/core.<locale>.po` and `modules/<module>/i18n/<module>.<locale>.po`; a game registers those catalogs with its own and translates only its own text. `tools/check_localization.js` checks every layer against its own catalogs. See `docs/LOCALIZATION.md`.

Games and links: a game is a Godot project under `games/<id>/`, registered by its `game.json` (`id`, the `modules` it uses with every module they require, extra `addons`, its own `autoloads` beyond `ContentDB` and `GameSetup`, and any `licensed_art`). Godot sees only files inside a project, so `node tools/link.js` links `gamebase/core/`, each listed module and each addon the game uses into it, as `res://gamebase/core`, `res://gamebase/modules/<module>` and `res://addons/<addon>` (directory junctions on Windows, relative symbolic links elsewhere). The links are Git-ignored and are the only copy a game has: nothing is copied, pinned or synchronized, and a game never edits the foundation through its links. It also writes the parts of the game's `project.godot` that follow from the manifests: the autoloads (the core's from `gamebase.json`, each listed module's, a module after the modules it requires, and the game's own from `game.json` `autoloads`), the translation catalogs and the addon plugins; everything else in `project.godot` belongs to the game, and validation fails when a committed `project.godot` differs from what the tool writes. Run it after cloning and after changing a game's modules; every tool that runs Godot on a game links it first.

A new game: `node tools/new_game.js --id <id> --name "<Game Name>"` copies `templates/new_game/` into `games/<id>/` (a game definition, an empty `game/game_setup.gd`, a content database, one start location and a runtime smoke), registers it with no module and links it. Add modules to its `game.json` and run `node tools/link.js --game <id>`; the modules install themselves. Validation creates such a game outside `games/` on every run and takes it through a new game, a save and a load, so the core keeps working without any module. A game can take `items` or `skills` alone, or any module with the modules it requires. The foundation's own unit tests run inside Farm1, the game that uses every module.
