# CI/CD, build and test efficiency

Applies when adding or changing CI/CD, the build and release chain, the test strategy or runners, or automated gates, and when reviewing how long they take. An ordinary local implementation still picks the smallest related verification and does not load the whole-repository flow because of this page. Commands, project boundaries and existing gates follow the current workflows, the `tools/` scripts and each game's `project.godot` and `export_presets.cfg`.

## P0 — speed does not break correctness or release safety

- Speed is not bought by deleting a necessary test, missing an affected consumer, swallowing errors, retrying until green without a basis, `continue-on-error`, lowering a coverage requirement, weakening the rule that an `ERROR:` or `SCRIPT ERROR:` line fails a Godot step, or loosening a safety or release gate. Before moving an existing required gate or changing how often it runs, prove equivalent coverage; a change of release policy follows the separate authorization boundary of `.agents/rules/project.md`.
- A reused verification result or build artifact must match the commit, the build inputs, the configuration, the engine and tool versions and the target that are being verified, and its origin must be trustworthy; a result from an old commit, a different configuration or an untrusted pull request is not a basis for a release. An export may stand in for a repeated import or validation only when it gives equivalent evidence; it does not stand in for the separate test, schema, configuration or release safety checks.
- Cancelling outdated runs applies only to verification and builds that can be interrupted safely. Publishing, a tag push and package uploads have side effects and do not copy the `cancel-in-progress` of a pull request; first confirm the concurrency group, idempotency and recovery after an interruption, so that concurrent runs do not overwrite each other and no release is left half done.

## P1 — control cost on your own initiative at design time

- **Look at the critical path first**: before adding or widening a gate, check how often it triggers, what each job really depends on, whether install, import, export or test work is repeated, and the runner queue time, the execution time and the total runner-minutes. Remove work that brings nothing first, then consider parallelism, caching or a larger runner; do not add a second entry point or scheduling that brings nothing in the name of speed.
- **Trigger by real impact**: the change selection covers shared dependencies, schemas, lockfiles, the toolchain and the workflow itself (`gamebase/`, `addons/`, `.godot-version`, `tools/`, the workflows); a pull request that changes nothing but some games' own `games/<id>/` directories covers only those games, and any other change covers every game (`node tools/ci.js games`); when the impact cannot be judged reliably, cover the related scope conservatively and do not treat "unknown" as a reason to skip. A pull request, a push, a reusable workflow and a release do not each obtain the same equivalent evidence again. A required check must not stay Pending forever because of a path filter; a conditional job or an aggregate gate separates "really not applicable" from failed, cancelled or should-have-run-but-did-not.
- **Layer the tests; do not block on everything by default**: locally run the related narrow verification first; a pull request keeps the fast checks and the necessary regression for what is affected; a release keeps the evidence it needs about the target artifact, schemas, save migration, safety and the smoke of the packaged build. Long full regressions, broad end-to-end runs, load tests, benchmarks and mutation tests go by default to a scheduled, manual or dedicated chain that fits their job, but a check that relates directly to this change or that the current policy requires still blocks; integration tests are not all moved to a nightly run mechanically.
- **Clear build boundaries**: an export step builds only the preset it was asked for; `node tools/export.js` validates before it exports unless `--skip-validation` is given, so a chain that has already validated the same commit, engine and inputs does not validate again inside every export, and full validation keeps its own entry point with a clear job. Install, import and export run once when the inputs are equivalent and the product can be verified for reuse; `--skip-import` and `--skip-validation` are used only when the earlier import or validation really exists and matches. Do not let every test shard or export target import and validate the whole project again, and do not introduce a more expensive packaging and download chain to pass a small artifact.
- **Isolate, then parallelize under control**: independent unit tests and jobs may run in parallel within the resource limits by default; tests that share autoload state, save files under `user://`, the `.godot/` import cache, a port or the `build/`, `dist/` and `artifacts/` directories are isolated first, and the necessary serial run is limited to the affected set. Headless does not mean isolated. Do not serialize everything forever because of a few conflicts, and do not pin `max-parallel: 1` or an equivalent single-worker setting without a basis. The concurrency and the shard count take CPU, memory, disk and the number of runners into account, to avoid nested parallelism, out-of-memory failures, resource contention and a jump in total cost.
- **A cache must have a net benefit**: prefer reusing the existing dependency and build caches; the key covers the related lockfile, the operating system, the engine and tool versions and the build inputs. A cache holds no credentials and does not carry release inputs across an untrusted boundary. A cache miss must still build correctly, and a hit is not a reason to skip a necessary verification. An ephemeral runner does no cache or disk cleanup that brings nothing; a persistent runner cleans only resources that the job owns and that really need cleaning.
- **A gate must be able to fail**: when the baseline is empty or not one check ran, the result is not a pass; skipped checks are counted separately and do not count as passed.
- **Fail early and within bounds**: cheap checks that stop later pointless work go first; heavy tasks with no real dependency are not chained into a waterfall. Jobs and long steps get a timeout with a basis; a retry is only for a clearly transient failure and has an upper limit. When something is slow or hangs, find the root cause first; raising the timeout again and again, a fixed sleep or more retries is not the default fix.
- **Scan by risk**: dependency freshness checks (new addon releases, the newest stable engine) and license checks of dependencies run when the vendored addon, a pin or a lockfile changes, on a schedule, or by hand; checks of source safety, secrets, permissions and release risk — what an export contains, that licensed source art is excluded — are still triggered by their real inputs and the current policy, and are not lumped together with the dependency checks and skipped.

## Runner traffic and execution budget

This repository uses GitHub-hosted runners only. The rules below hold for them; the clauses about a persistent runner apply only if one is ever introduced.

- Finish the implementation and the related narrow verification of one batch of changes locally, then combine it into one necessary push; a push, a workflow dispatch or a rerun is not a command for trial and error item by item. While a run for the same commit is still executing, do not start another.
- Installs prefer the download cache the runner already has and go to the network only for what is missing; keep the version source of truth, the frozen lockfile (`npm ci`), and the integrity and safety checks. Do not routinely empty the package cache on a persistent runner, and do not upload or download a whole engine, a whole set of export templates or the dependency tree as a remote cache by default.
- A status query serves only to decide the next step, and a result that is still valid is reused; without a new event, a changed input or a real need of the operation, do not fetch the status, the full log or a large file again. Cancelling a run keeps to the side-effect and recovery boundary of P0 on this page.

## Moving work forward during a long task

- **Waiting does not block independent work**: separate the next step that really depends on the result of a long task from items that can move on their own. While an export, an upload, a CI run or a release workflow is in progress, continue the other authorized work; independent work for another export target, tidying text and maintaining rules do not stop because one target is waiting.
- **Parallel does not mean running the same thing twice**: control concurrency by CPU, memory, bandwidth and execution slots; avoid conflicts between runs of the same build, uploads for the same release, changes in a shared working tree and changes to published state. Reuse the existing run, candidate, cache and receipt; do not open an identical task for the sake of parallelism, and do not change the inputs of a candidate that is in flight.
- **Wait only at a real dependency**: wait only when the next step must use the result of the long task. When the user explicitly does not want to wait, complete the other items that can be done, then save the exact target, the task identifier, the last confirmed state and the next step, and end the round; do not keep polling, and do not start a background watcher or a new pipeline on your own. An external wait stays marked as unfinished and does not pass for a delivery.

## Release delivery and repeated operations

- When the user asks for a release to be published, accept it by reading back the published release for the exact version and tag, with its packages, `RELEASE_MANIFEST.json` and `SHA256SUMS.txt`; a Git commit, a push, a started run or a green CI does not stand in for the published result.
- Within the authorized scope, move forward first the operations that directly affect the delivery. Correct text, tools and generalizations stay stable; do not withdraw a whole batch and rewrite it because of a local problem, and do not turn engineering improvements unrelated to the current release into a new condition to wait for.
- Before every rerun, re-export or re-upload there must be a concrete failure cause, a fix or a changed input as the basis; while the existing material and verification are still valid, reuse them directly. Keep to the existing safety and authorization boundaries, and do not replace solving the problem with more runs or repeated status queries.

## Time budget and performance acceptance

The table below gives initial design targets for a new or changed ordinary fast chain. They are not measured results of the current pipelines and not an instruction to change existing timeouts automatically:

| Chain | Initial target |
| --- | --- |
| Related local verification of an ordinary local change | within 2 minutes |
| Critical path of fast feedback on an ordinary pull request | within 10 minutes |
| Machine-executed critical path of an ordinary release, including the required CI before it | within 20 minutes |

- Runner queue time, manual approval and processing time on an external platform are recorded separately and still count towards the user's end-to-end wait; the experience is not made to look better by leaving them out. Cold starts, cold and warm caches, runner sizes and target environments are compared separately; the three-target export, the long-horizon soak, the weekly engine compatibility run and a necessary full regression build their own budgets from measurements and do not mechanically take the table above.
- When data exists, record a comparable baseline and the result of this round; use the median and P95 once there are enough samples, and do not conclude an improvement from the swing of one run. Without run data, write "static assessment / to be measured" and give the basis of the cost judgment; do not make up a speed-up, and do not start expensive pipelines again and again to collect measurements.
- When a target is exceeded, a new heavy blocking step is introduced, or there is a clear regression against a comparable baseline, explain the independent verification value, where the time goes, the alternatives considered and the condition for improving or dropping it; record this in the existing pull request description or the documentation of the matching owner, and do not set up a second budget ledger. Do not delete a gate or shorten a timeout to fake meeting the target.
- The completion note covers at least: which verification was chosen, why it is enough, the effect on time and cost, how repeated work was avoided, and the performance items still not verified. When the function passes but there is an unexplained performance regression, do not declare the optimization done.

## Minimum verification

When a workflow changes, run the workflow assertions in `tools/repository.test.js` (`node --test "tools/*.test.js"`, also part of `node tools/validate.js`), and verify what actually changed in the triggers, dependencies, caches and artifacts or cancellation logic; when only rule text changes, use `node tools/validate_rules.js --strict` and a review of the related rule scenarios, and do not run the full game tests or trigger a remote release because of it.
