# Save data (`gamebase/core/save/**`)

`GameSaveManager` (`gamebase/core/save/`) keeps as many slots as the game's `GameDefinition.save_slots` (`get_slot_count()`), each with the player's own save (`slot_<n>.json`) and an autosave of its own (`slot_<n>_auto.json`, which `AutoSave` writes, when the player passes out too), so an autosave never replaces what the player saved: a slot continues from the newer of the two (`SaveKind.LATEST`, the player's own on a tie), and the pause menu loads the player's own (the autosave while there is none). A load leaves the slot going on from the save it loaded: the other one, when newer, is deleted, so Continue never brings back progress the player went back from. Each save is compact JSON under `save_directory`: a temp file is promoted to the primary and the previous primary, when it is a save this build loads, is renamed to the backup. What a file holds is read once and kept until the file changes (its modified time and length), the registered sections change or the content does (`SaveFiles`), so a menu asking `has_save()` reads nothing again. A load covers the screen (`Transition.cover()`), holds the world still (`LOAD_LOCK`) and loads the location in the background before any service changes; the return to the title changes the scene behind the transition too. `SAVE_VERSION` is the format version. The engine behaviour described here was confirmed on Godot 4.7.2.

## P0

- **One format, no compatibility code**: a save loads only when its `version` is the current `SAVE_VERSION` and it holds every registered section. There are no migrations, no fallbacks for older formats and no preservation of data this build does not understand. A change to what a save contains or means raises `SAVE_VERSION`; saves of other versions then no longer load.
- **A save names current content only**: on load each service drops entries whose ids are not current content (items, quests, animals, placeables, crops, processing outputs) or whose values are malformed. Nothing is kept for content that might come back.
- **A new section is one change**: it needs all of the following together.
  1. Raise `GameSaveManager.SAVE_VERSION`.
  2. Register a `SaveSection` for it: the foundation's own sections in `GameSaveManager._register_core_sections()` (the session's time played in `GameSession._ready()`), a module's in its `GameModule` class (`gamebase/modules/<module>/<module>_module.gd`), which the core's `GameModules` autoload installs in every game that links the module. `order` is the restore order: `apply_snapshot()` restores global state before the saved scene is instantiated, and the order between services matters, so read the comments on the existing registrations before choosing it.
  3. Register a new-game step for it (`GameSession.register_new_game_step()`), otherwise a new game inherits the previous session's state.
  4. Runtime state derived from several sections is rebuilt by a load step (`SaveManager.register_load_step()`), which runs after every section is restored.
- **Store stable ids only**: a node path, a scene file path or a list index is not a durable identity; the save names its location by Location id, in the core's `place` section with the player's position when a player walks the world. A game with no one walking it (cards, a visual novel) saves its location alone; only the location is required to save.
- **A write is checked**: `SaveFiles.write()` reports success only when `FileAccess.store_string()` returned `true`. A save whose temp file could not be written stops before the primary or the backup is touched. The player reads why in plain words (`write_save()` returns them, `save_game()` sends them with `save_completed`, and a failed autosave is a toast), and the log names the file that could not be written.

## P1

- **Core never names a module or a content id**: `GameSaveManager` and `GameSession` only iterate what was registered with them and read the game's facts (start location, home, starting clock) from the `GameDefinition` named by the `gamebase/game_definition` project setting. A module service is wired in by the module's own `GameModule` class, never called from `gamebase/core`, and reads what the game sets for it from its `ModuleSettings` (`ItemsSettings`: the starting money and items).
- **Where persistent state lives**: seventeen services own a section of the save: `place` (the save manager's own: the location and the player's position), `random`, `session` (the time played), `playthrough`, `clock`, `vitals` and `world` (core), and `inventory`, `wallet`, `hotbar`, `relationships`, `npc_memory`, `quests`, `skills`, `buffs`, `shipping`, `fishing_state` (modules). Everything else that persists (animals, buildings, storage, mail, town projects, contracts, collections, farm plots, mine state and more) keeps its values in `WorldState` under its own keys, and `WorldState` is the `world` section.
- **A value that has been saved and loaded is not the value that was stored**, because of what JSON does to it:
  - Every number comes back as a `float`. `3.0 == 3` is true, but `match value:` with a `3` branch does not match `3.0`, and `{3: x}.has(3.0)` is false. Read a whole number with `SaveValues.whole_number()` (`gamebase/core/save/save_values.gd`), which gives null for a fraction, an infinity or a value beyond 2^53 (`SaveValues.whole_number_or()` gives a fallback instead, and `SaveValues.count()` reads a quantity, a day or money as a whole number of 0 or more), before a `match`, a dictionary lookup, an array index or a comparison against an enum. An int further than 2^53 from 0 does not come back as it went in; a float does, since the save writes every digit.
  - A `StringName` comes back as a `String`. Ids read from a save are converted with `StringName(String(value))` before they are used as ids.
  - Integer dictionary keys come back as string keys.
  - `Vector2`, `Color` and other engine types are written as their text form and come back as a `String`. Store their components, as the `place` section stores the player's `x` and `y`.
- **The player's profile is not a save**: `GameProfile` (`gamebase/core/profile/`) keeps achievements and profile flags across every save in `user://profile.json`, which a new game, a load or a deleted slot never touch. It follows the same one-format rule under its own `PROFILE_VERSION`: a change to what the profile holds or means raises it, and a file of another version reads as an empty profile; within its version it keeps only well-formed values and current achievements, as a save does. A test or runtime check that changes it points `profile_path` at a file of its own first; every game's GUT run does so in the core's `gut_pre_run.gd`.
- **Closing the window is a save point**: `AutoSaveService` asks for an autosave (`write_save(true)`, the slot's autosave) on `NOTIFICATION_WM_CLOSE_REQUEST`. With `auto_accept_quit` on, the handlers run to completion before the tree quits (confirmed on Windows), so that save stays synchronous; an `await` in it would never finish.
- **A save result is already translated**: `save_completed` and `load_completed` carry text in the current language, and `get_save_block_reason()` returns translated text or an empty string. Each is a whole sentence for the player, a failure included, so a consumer shows the message as it is, with no prefix of its own, and tests a block with `is_empty()`, not against a sentence.
- **What a slot shows is read from its save**: `get_slot_summary()` gives, of the newer of its saves (`autosave` tells which), the date and time, the location (`location_name`), the time played (`play_seconds`) and the lines the modules and the game add with `register_slot_detail()` (the items module's money), each told from the save itself (`PersistentWorldState.read_saved()` reads a world value), never from the running session.
- **A slot this build cannot read is never replaced unasked**: `get_slot_summary()` reports it as `unreadable` (`has_files()` without `has_save()`), the title screen says so, and a new game asks before `GameSession.start_new_game()` deletes it. Its contents are still never read or converted.
- **An activity ends before the session moves on**: a service that holds the player in an activity (a fishing cast, a minigame) and takes a lock or blocks saving for it registers how to end it with `GameSession.register_activity_end()`. Passing out (`GameSession.pass_out()`: a defeat, a late night), a load and the return to the title call `GameSession.end_activities()` first, so their save is never blocked by what they interrupt.
- **Nothing saves while the session changes**: `get_save_block_reason()` refuses while a save loads, a new game starts or the player travels, and a second `load_game()` while one runs is refused.
- **A node that a load or a travel frees never awaits it**: a menu starts `SaveManager.load_game()` or `GameSession.continue_game()` without `await` and listens to `load_completed` for a failure; a coroutine of a freed node errors when it resumes. Code that must go on after a travel awaits `WorldTravel.go_to()` from an autoload.
- **A test that writes a save uses its own directory**: it sets `save_directory` to its own `user://` directory and calls `select_slot()`, restores the original directory afterwards and deletes the slots it wrote (`gamebase/core/test/test_game_session_start.gd`).

## Verification

`games/farm1/test/runtime/long_horizon_soak.gd` performs real disk save and load round trips; a change to a section or to a load step is not verified until the soak has run, so use `node tools/validate.js` without `--skip-soak`.
