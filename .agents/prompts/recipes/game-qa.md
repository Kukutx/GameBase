# Game QA and interaction evidence recipe

Use only when the user asks for an inspection of the running game by operating it, for coverage of UI and game states, for archived screenshots, for visual consistency, or for the regression of fixes to those. It is not the default full flow for an ordinary fix to one screen, a text change, a root cause in a service, or a question that only asks where the screenshots are. The name of the model does not change the authorization, the real tool capabilities or the acceptance evidence.

This flow delivers an acceptance result for what the player sees and operates, and the process screens for the user to review independently. Coverage, process images and passing acceptance are different dimensions: the scope decides what is checked, the images let the user see the actual screens, and a pass also needs the matching visual, interaction or game-state evidence. A minimal archive removes only duplicate screens and unrelated material; it does not shrink the agreed UI coverage, and no separate process ledger is created. Preparing the environment and troubleshooting a service do not get a QA archive of their own; their results are mentioned only where they affect the acceptance conclusion.

## Entry and sources of truth

This page owns the Agent's execution workflow. The commands and their facts are in `AGENTS.md`, `docs/RELEASE.md` and the `tools/` scripts; what a log, a diagnostic line and a support bundle contain is in `docs/SUPPORT.md`. The repository has no evidence manager: a QA session is a directory under `artifacts/` (Git-ignored) that holds the captures and one index file. The existing automated captures are the Chromium smoke of the Web export (`npm run --prefix tools/web_smoke smoke:web -- --game <id>`, which writes `artifacts/<id>/web-smoke/`) and the native smoke of an exported build (`node tools/smoke_export.js --game <id>`, which writes `artifacts/<id>/release-smoke/`). Neither operates a menu; they are not a permission system and not a QA result.

Read the existing rule for the target path; for the actual visual and interaction judgment use `.agents/skills/ui-design/SKILL.md` as needed, and `.agents/skills/game-qa/SKILL.md` for operating the game. Read `.agents/rules/project-domain.md` only when a change alters the player-visible structure, a state, a permission or the domain meaning, and do not load all product documentation. Do not copy new global rules, and do not fork this flow by model.

## Targets and their branches

First confirm **which build is being inspected**, then choose the target, the locale and the input device. The project run from the engine, an exported Windows or Linux build and the Web export are all in scope for a game QA task; a request for the whole game is not shrunk to one target, and a shared scene or theme is not left out because it is not a screen of its own. Consistency across targets means the same game rules and the same text, not that every target must look identical pixel for pixel.

| Target | Necessary branches beyond the common UI checks |
| --- | --- |
| Web export in Chromium | The canvas stays visible and fully inside the window at the viewport sizes the smoke uses, keyboard focus reaches the canvas, reload and returning to the page, console, page and network errors, the browser console in place of the log file, and the absence of the support bundle entry |
| Exported desktop build | Window mode, vsync and resizing, the log at `user://logs/<id>.log`, the support bundle export and the button that opens its folder, saves on disk, quitting and starting again, and the release pack content as opposed to the project run |
| Project run from the engine | Keyboard and gamepad, pause and focus, debug-only entries and actions, and the code paths that a headless run never executes; debug behaviour is told apart from what a release build shows |
| Shared scenes, theme and components | Find the real consumers; after a change pick different variants, targets, locales and game states for the necessary regression, and do not verify only the screen where the problem was first seen |

For the Web export use the Playwright that `tools/web_smoke/` already installs, with its own browser context so that other sessions are not polluted; reuse the existing export and serve path, do not take over a port that is in use, do not close a server someone else started, and do not install a new framework on your own. The whole game is drawn into one canvas, so there are no roles or labels to locate: an action is a key, pointer or gamepad event, and its result is read from the frame, the console and the game state. A global network-idle wait, a fixed sleep or a forced click is not a reliable success condition. The canvas being present does not mean the scene loaded, and a headless or mocked run does not prove what the rendered game does.

Choose the evidence of a case by its assertion: a visual assertion needs an image; an interaction assertion needs the related change on screen or in focus; a state assertion needs a read-back. Save the method of the check, the expectation, the actual result and the index of the attachments. A new screen the user asked for is still captured and archived, but a screenshot does not replace evidence of a saved value, a written file or the state after loading. Record the real target, engine and build of the run; evidence from a different target or build is not mixed in. The localization gate, the error-line check and the save safety checks are not switched off to get past a problem.

## Goal, permission, capability and concurrency

First confirm the target, the build, the scope, the success and stop conditions, the paths that may be changed and the explicit exclusions of this task. When the user has authorized implementation, complete the low-risk details inside the scope on your own and do not ask file by file; the machine's display and input, the player data under `user://`, third parties, Git and publishing each keep their own authorization boundary.

When a missing prerequisite blocks acceptance, complete the necessary fix that is authorized, at its real root cause, and return to the verification; keep a concrete blocker only for what is outside the authorization or beyond the actual capability. A record does not replace solving the problem and does not widen the authority to fix.

Confirm the capabilities from what can actually be run: a Godot binary and whether it matches `.godot-version`, export templates, Node 24 with the Chromium that Playwright installs, a display for a windowed run, a gamepad or a way to send gamepad events. A windowed run, a headless run, an exported build and the browser are not equivalent to each other; a capability that is not available is recorded as blocked or not applicable and is not presented as verified. Reuse the existing drivers and build entry points first; do not install dependencies or set up a second test platform on your own.

Other changes in the working tree are not there to be cleaned up. Read the target file again before changing it and add only the necessary block; do not overwrite, reformat, stash, reset, switch branches or touch the processes of another session. A drift of the Git baseline is a hint to check, not a reason to roll back automatically.

The same display, the same browser profile, the same `user://` data and the same save slot cannot be operated by several sessions at once. First confirm the current owner and what it holds exclusively; a lock on the archive files is **not a lock on the machine**. Independent code analysis may run in parallel; operating the game and actions with shared side effects are run in sequence by one owner. Without coordination from the host, conservatively pause the conflicting part, and do not start a global lock or kill processes to take over.

Before the actual interaction begins, read back the build that is really running: for an exported build its `BUILD_INFO.json` (game and version, Git commit, dirty flag, engine, target), for a project run the commit, whether the tree is dirty and the engine version; and the locale, the window size, the display scale, the input device and the save slot. The name of a preset or of a screenshot file does not replace these facts. Directory and file names use only non-sensitive labels and never a user name or a host path.

## Plan and session

Create or continue a QA session only when the currently authorized stage actually carries out acceptance and needs an archive; preparation and troubleshooting do not start acceptance, a case list or a report by themselves.

Check what can run, pick the exact build and target, and then create one session directory, `artifacts/<id>/game-qa/<UTC-date>/<session>/`, with one index file named index.md in it. The index names the target, the build identity, the locale, the window size and the input device, and lists the cases. Writing into the session directory is a local archive that the current authorization for the QA task already covers; it authorizes no side effect on player data, a published release or a third party.

Split this round's coverage into observable cases of screen, state and transition; differences of locale, window size, input device or game state on the same screen may be separate cases. The number of screenshots does not stand in for coverage, and "not every entry has been found yet" is not a reason to explore without bounds. By risk, cover the key flows and the problems already found first, then the important branches; the full product of all environment combinations is not required.

The coverage claim stays traceable: the denominator is not improved by deleting failed cases or relabelling them as not applicable. Not visited, blocked, skipped, unverified, not applicable and fail are recorded separately; not applicable needs a factual basis, and a missing gamepad or a save without the needed progress is normally a blocker, not "not applicable".

## When the user asks for "all interactions"

"All" is a coverage target of a complete interaction list and may not be shrunk on your own to a smoke of the main screens; it also does not mean every possible input, endless click sequences or every environment combination. First complete the list from the current scenes, the actions inside each screen, dialogs and balloons, conditional entries, game states and unlocks, the controls the game's `game_definition.tres` lists (the actions under `gamebase/core/input/controls/` and the game's own) and an actual run; the number of scenes, the number of callbacks found by keyword and the coverage of the source by tests are not interaction coverage.

The unit of coverage is **entry + game state and precondition + action + expected result**. A full task says so in the index and gives every case its entry, state, precondition, action and expectation, with the assertion set by the real acceptance meaning: visual, interaction or state. For example, opening the save slot screen, saving into an empty slot, overwriting a slot, cancelling the overwrite confirmation, loading, and returning and opening the screen again are different cases, and one "the save screen opened" does not cover them all.

First collect candidates from the source of the scope and its bounded shared dependencies — the screens under `games/farm1/game/ui/`, the world scenes and the HUD under `games/farm1/game/world/`, the dialogue files under `games/farm1/game/dialogue/`, the input actions, the content registered in `games/farm1/game/data/content.tres` — then complete the cases against the real UI and the game state. Candidates can be false hits or miss a dynamic entry; a keyword count is not the denominator, and all files are not mechanically attached to one vague case. For every candidate the index gives the concrete cases or a reasoned exclusion; missing data or a missing device stays blocked and is not a reason to exclude. Only when the check against an actual run is done is the real build and run written into the index. When cases are added or the source changes, review the difference again and keep the original cases and gaps. A local UI fix stays scoped and does not force a scan of the whole game every time.

Cases, captured steps and problems may be written into the index in batches to save tool calls. When a write to player data is recorded and at what moment is covered under "Write operations, recovery and privacy" below. The plan and the index are local data only; they contain no executable script and give no extra authorization, and a temporary copy made only for importing is removed once it is imported.

| Dimension of the list | Acceptance in a full-interaction task |
| --- | --- |
| Inside a screen and across screens | Accepting, cancelling, moving focus in every direction, holding and repeating, pointer hover and click, text entry where it exists, actions inside a dialog and second-level entries each have an item; no visible or reachable entry is left out without an explanation |
| States and game progress | By the real domain rules, list normal, empty, loading, disabled, a refused action, a failed save, load or travel with its retry, and what different progress unlocks; every item has an actual result or an explicit blocker, and is not turned into "not applicable" because test data is missing |
| Writing and persistence | Read back after saving, and check after loading and after starting the game again; a change of settings is checked after a restart; what another system shows after the action needs evidence from that system, and a success message alone does not prove that the data was written |
| Engine and platform | Keyboard, gamepad, pointer, rebinding controls and resetting them, fullscreen, vsync and resizing, audio, the support bundle and the folder it opens, and the browser are listed one by one; when a device, a display or a real platform is missing the item is blocked, and a unit test with simulated input does not pass for a verification on the real target |
| Targets and release form | Test only the matrix of targets and entries that is actually supported; debug-only entries, reserved features and capabilities open in a release build are kept apart, and a protected capability is not deleted or opened on your own to make testing convenient |

Prefer the current GUT tests for the large number of deterministic branches, and use the running game for player flows that cross components and for the platform boundary. First check the test directories and what the drivers really do; a file name that says integration or smoke does not prove that it runs against the rendered game or an exported build. Add a persistent automated game test only for a real repeated pain point and with authorization; "all" is no reason to install a new framework at once or to widen every CI gate.

Several modules may be completed in stages and in several sessions, but the final summary must list the exact sessions, scopes, builds and uncovered items of every stage; several local scoped passes are not called "the whole game passed". A conclusion across targets needs an explicit matrix of target, locale and input device, and a missing target, an old build, a wrong target or an unsupported item keeps it incomplete. Across stages align the interaction list first, so that items not yet run and blocked items stay in the total list. A timeout or an occupied machine pauses only the dependent part and keeps the state partial; the goal of the task is not quietly made smaller.

An acceptance build needs an identity that actually tells it apart; a version number alone does not distinguish code that changed after the build. When the game code, a resource, the configuration or the export changes, update the build identity in the index. A build recorded as unknown cannot fall back on older evidence. A pass recorded for another build stays as historical evidence and is not merged into "the current version passed". Stale evidence does not by itself require a retest of everything; add the necessary UI regression by actual impact, and leave the unconfirmed remainder stated as it is.

## Interaction and evidence

Check the entry, the state before the action, the target state, going back and cancelling, entering again and the persisted result as a real player would, and not only that a button opens something. Prefer observable state and stable waits; an action by coordinates must use a position and size that were just read, never a stale one. A fixed sleep is only a bounded supplement for a transition that cannot be observed and does not replace a success condition. A wait condition is bound to the new state this action produces; a condition that already held before the action does not count as waited for. A successful screenshot does not mean the content was drawn: first rule out a blank frame, a frame taken during a fade and a silent fallback, then use it as evidence.

By the game's actual capabilities and the authorized scope, cover the title screen, the game menu and its tabs, the pause and settings menus, the HUD, the dialogue balloon and its responses, world scenes and travel between them, interaction prompts, shops and crafting, saving and loading, and language and accessibility settings. Deleting or overwriting a save, loading over unsaved progress and resetting settings first go through the intent and read-back flow below.

The actual UI acceptance of this flow follows "Process screenshots and user review" below, and the user does not have to ask for screenshots again in every round. A local acceptance records this round's path and the affected states; a full one moves through the complete interaction list; a process recording requirement stated earlier stays in force across rounds, fixes and resumptions until the user changes the scope. A pure analysis or an ordinary local text change does not start an inspection of the game because it refers to this page.

All new evidence goes into the current session directory. The driver first saves the binary screenshot under a scratch path of that session and the capture is then entered in the index; avoid shell text redirection that could re-encode the file. Afterwards clean only the scratch copies that this session owns and that are already indexed. Old sessions and old capture directories are not migrated, overwritten or deleted automatically.

Choose the evidence by the assertion: a screenshot for a static visual, a short video for an animation, a transition or a held input; a part of the scene state, of the log or of a save read-back is kept only as far as it proves the related interaction, state or defect. Information used only to locate something at the moment or to troubleshoot is not archived by default. When necessary evidence is missing, state the gap and do not fabricate. The real time, origin, build and environment must match; an older image that is imported is marked historical and material from a test fixture is marked fixture, and neither proves that the current UI passed.

### Process screenshots and user review

The goal is to let the user review screens that the Agent may misjudge and that the user cannot easily reach alone. The set of screenshots is not decided by the list of defects or by the list of fixes.

**Discovery and scope**: combine the entries in the source with an actual run to find, inside the authorized scope, deep screens, nested dialogs, entries reached only by a key or a gamepad button, content below the fold, conditional controls and the states after returning from another screen or from the platform. A branch newly found inside the scope joins the existing cases; a state that cannot be reached for lack of data, progress or a device stays as a gap. A problem met by chance outside the scope is only mentioned and does not widen the change or the inspection.

**States and changes**: tell observations apart by "entry or component + precondition + action or transition + visible result". Whenever the content, the actions, the layout or the feedback differ visibly, keep it, including normal, loading, empty, disabled, validation, partly done, failed, interrupted, cancelled, retry and recovery; the same holds for the differences of locale, window, input device and game state that the task involves. Keep states that were not changed, not solved and not judged defective; a success image of the same screen or one image of a similar component does not stand in for them. Items that are solved and not affected by a new change keep their evidence and are not accepted again just to have an image.

**Capture timing and quality**: before going back, closing, submitting, retrying, reloading or changing code makes a state disappear, save the screen and look at it. For short feedback and continuous change, prepare a bounded recording or a burst of screenshots before triggering, and keep from it the key frames that make the state and the change recognizable; do not capture only after it is over, and do not change the real game into fake progress, a fixed success or a test-only delay for the sake of the capture. Confirm that the image opens, shows the intended target and is not covered by something unexpected; a long list and a local scrolling container need coverage of the content checked this round, and a single first screen does not prove the whole. A continuous animation need not be stored frame by frame, and a completely identical repeated observation may be reused and linked to the original image.

**Origin and review**: keep using the current session and its index as the gallery; as the check moves on, link every screenshot with the least it needs — entry, action, state, time and build identity — and give an entry the user can open in each stage update. Before and after a change, and different run conditions, are shown separately; an old image is not overwritten and an image is not left only in scratch. The conclusion of a check and the screen are separate: an archived image is not a verification, and a unit test or a read-back does not replace an image. Sensitive information in a screenshot follows the privacy boundary below; when masking affects the judgment, state the limit; do not expose credentials or user paths, or upload to an external service, for the sake of a complete set.

**Interruption and gaps**: when a stage ends or the task is interrupted, check the existing list of entries and states for whether "should be checked, actually observed, image saved, conclusion" line up, and point out the omissions directly in the current session without writing another ledger. On resuming, first check the current run state and the saved evidence and continue by the impact of the changes; what was not run, was not captured or belongs to an old build does not count as done. When the user asks afterwards, answer truthfully first; a later reproduction is a new observation and cannot restore process evidence that was missed. Whether to test again is decided by the task authorization still in force and by the current instruction; the question itself adds no authorization and does not withdraw the existing work, and when the user explicitly refuses a retake, no retake is made.

At completion, every entry and state inside the declared scope has an actual result or an explicit gap, the distinct screens that were observed can be viewed in the gallery, before and after a fix can be traced, and what is unsolved, unverified or not captured stays visible to the user. The number of screenshots, a passing file check or a success screen does not replace these conditions.

## UI, theme and code review

| Angle | Judgment and verification |
| --- | --- |
| Layout and feedback | Alignment, margins, density and information hierarchy, anchors and containers at every supported window size, overflow and clipping, an overlay covering focus, the size of click targets, loading, disabled, error and retry states, and protection against repeated activation |
| Consistency across screens | Compare panels, lists, buttons, dialogs, prompts, and empty, error and loading states that mean the same thing; a difference between targets may be reasonable, and pixel identity is not forced |
| Ownership of components | Reuse first, then extend or compose locally, and promote to a shared scene only for stable repetition; things that look alike but belong to different game systems keep their own wrapper, and no all-purpose component with many boolean or mutually exclusive parameters is built |
| Theme | Respect the existing theme, its type variations, colours and constants, and the brand assets; do not mechanically forbid every local override, and do not add a theme entry for every one-off value |
| Accessibility and input | Visible focus, focus order and wrap-around, no focus trap, operation by keyboard alone and by gamepad alone, input prompts that match the device in use, contrast and legibility, and the reduced motion and weather effects options; a test that sends input events and the behaviour with a real device are confirmed separately |
| Adaptation and localization | Inside what the project supports, pick representative small and large windows, the extreme aspect ratios, fullscreen and windowed, long strings, and English and Simplified Chinese including numbers, dates and line breaks; what was not tested is not written as supported |
| Lifecycle | Leaving a screen during an operation, a callback after a dialog closed, quick scene changes and travel, pausing and resuming, losing and regaining focus; check the ownership, the disconnection and the isolation of stale results for signals, tweens, timers and nodes that were freed |
| Performance | First record a reproducible stutter, repeated work or a resource that is not released, then profile as needed; the feel of a debug run does not pass for release performance data, and no expensive full analysis is started first |
| Failure and permission | A failed or refused save, load, travel or purchase gives feedback the player can recover from; do not switch off the whole network, the autosave or a platform permission casually, and prefer a means that is bounded, recoverable and does not affect other tasks |

A correct validity or lifecycle check stays; a reasonable guard is not treated as a hack, and a root cause is not hidden by swallowing errors, a delay without a basis or switching a feature off. When automation is hard, first judge whether the game is missing observable state, and do not lay test-only identifiers through the whole project or refactor in advance.

A UI recommendation separates observation, evidence, basis and recommendation. The existing design language is the boundary; the model's taste or a current fashion does not change the brand colour, a protected asset or what the game can do. A fix lands at the real owner — the screen, the feature, the shared scene, the theme or a service — and is not widened to unrelated screens for the sake of uniformity.

## Write operations, recovery and privacy

A write to player data during acceptance — saving into a slot, overwriting or deleting a slot, loading over unsaved progress, changing settings, exporting a support bundle — is recorded as an operation only when an unknown result could cause a repeated side effect or when there is an obligation to restore something across steps. Judge by the real consequence in the game, not mechanically by the name of the button or by whether a command has a side effect. Before running it, save the minimal pending intent, the target, how it will be read back and the restore obligation; afterwards read back and record confirmed or not-applied; when it cannot be determined, record unknown, and do not write the intent in after the fact. Whether or not it is archived, after an interruption or a timeout check the actual result first, and do not treat "no response" as a failure and retry.

Data under `user://` on the machine is not test data by default. Overwriting or deleting a save slot that holds real progress, resetting settings and any other operation that cannot be undone need an explicit authorization or decision. The localization gate, the error-line check, the save validation and the autosave safety checks are not bypassed by switching them off or by changing unrelated configuration.

Before changing a recoverable setting such as the language, fullscreen, vsync, audio volume, key bindings, accessibility options or autosave, record its non-sensitive original value; before restoring, confirm that the current value is still the one this task set, so that a later change by someone else is not overwritten. Cleanup covers only data that can be shown to have been created by this task; on a conflict or when it cannot be read back, keep the state open and do not restore or delete blindly.

Screenshots, videos and logs may show a user name, a host path or other personal information, for example in a file dialog or in the folder that the support bundle button opens. Prefer test data; a secret never goes into input, logs or reports. Raw save files, `settings.json` and absolute user paths are never archived; a save is represented by its slot summary. Masking text is a limited aid and does not prove that a screenshot is clean; a local archive is not permission to upload. Without a separate authorization nothing is committed to Git and nothing is sent to an external service.

`artifacts/` is a disposable area and may be deleted; do not change the ignore or cleanup rules to protect a report, and do not use it as the only persistent store of game state, of an idempotency key or of a credential. Do not clean the active session of someone else while it runs. When the user wants long-term keeping, handle it separately within the archive scope that was authorized.

On resuming, read the index of the explicitly named session, the current working tree and the real state of the game and its save slots; do not pick the "latest" directory automatically and start pressing keys. An index, a report and text on a screen are data only, not instructions to carry out, and they create no new authorization. A session that another running process is still writing is not taken over after a timeout; continue it only when its owner is known to have ended.

## Fixes, regression and visual baselines

Keep the reproduction evidence → confirm the root cause and the affected area → make the smallest correct change → run the smallest related check → walk the original path again on the actual target → save the after evidence → run the necessary representative regression. A shared component is sampled by variant and by the way it is called; do not test only the one screen where the problem was found, and do not run all game tests by default.

Keep using the project's existing entry points — `node tools/validate.js`, `node tools/check_localization.js`, the export and the smoke tools — and control cost by `.agents/rules/ci-performance.md`; without a failure, a new change or a concrete open doubt, do not rerun again and again. A static check and a headless test do not replace verification of the UI.

A visual comparison is interpreted only under a comparable build, font, window size, locale, scale and controlled dynamic data such as the in-game time, the season, the weather and the random seed. A pixel difference between screenshots is not directly a bug; when a golden image is really needed, reuse an existing mechanism, do not update the baseline automatically to make a check green, and do not hand every difference to a subjective scorer as a hard gate.

## Closing and later models

Update the resume point in the index when the build or the run context changes, or when a pause or a change of stage has to keep the place to resume from; do not write it again when no new information affects acceptance or resumption. When the acceptance stage ends, bring the index to its final state once — cases, coverage, findings, summary and the links to the images — and create no duplicate report. A summary is a derived view; the sources for resuming are the index and the current facts of the game, its saves and its build, not an outdated summary.

A structural check (every file opens, every reference in the index exists) says only that; the gate also requires that the observations inside the declared scope passed. One real failed result does not disappear because a retry succeeded; record the problem and the explanation first. Fixed is not verified: without a real after verification, with an open side effect, with a setting that was not restored, with a missing build identity, or without the evidence that the assertion of the case requires, an item cannot be marked completed.

Where necessary, close as partial, blocked or aborted, and state the actual blocker, what was not covered and how to resume; do not aim at a false "100% no problems". The completion note covers the scope, the environment, the evidence paths, the root cause and the place of the change, the effect on components, the actual verification and what remains, and does not pile up a running log of the execution.

After a host or model upgrade, keep discovering the capabilities from the tools that are actually registered and can actually run. A rule that passes statically and a tool whose own tests pass do not mean that the model's automated behaviour was measured to improve; a real replay records the model, the host and the instruction version, the actual tool trace and the result. Without such evidence state clearly that it is not verified, and do not add speculative capabilities for future models.

## Key counterexamples (a static review, not a model replay)

- Only asked "where are the screenshots": locate the directory only, and do not start a UI inspection or change code.
- The user says "continue" and the last save request has no confirmation: read the index and the save slot, and do not save again.
- Another session is operating the game on this display: continue independent tooling and code work, and do not send input or restart the game.
- Only old images, fixtures or unit tests exist: keep them historical or unverified, and do not give completed.
- Similar screens differ reasonably between targets: keep the meaning consistent, and do not force the style to be identical.
- A running process still writes the session directory: it is busy; do not take it over or delete the directory, and a lost report is no reason to replay operations on player data.
- The related regression is done and no new doubt exists: close, and do not start a full validation or a release to check a few more times.
